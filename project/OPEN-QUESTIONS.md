# Open questions – decisions with the product owner

New questions are added to the first table. Once decided, the row moves to the second table (with cycle and ADR reference).

## Open

| ID | Question | Context / options | Blocks | Status |
|----|----------|-------------------|--------|--------|
| Q-021 | Rust SDK (D2): which execution model is primary? | **(a, recommended)** blocking by default: `App::run()` brings its own runtime, state updates are sync and non-blocking, handlers are plain closures; only consumer requests are `async` (each with a `_blocking` twin); `run_async()` for tokio users. Same model as the C ABI. **(b)** async-first: every call is `async`, the app needs `#[tokio::main]` – idiomatic for network code, but more ceremony and a second model for C. ADR-0020 §2 (C-042). | P4 | open (C-042) |
| Q-022 | Rust SDK (D2): how typed is the Config access? | **(a, recommended)** P4 ships string-keyed typed getters (`values.number("Polling", "Interval")`) on top of the validated Config DataSet; a `#[derive(Config)]` for typed structs is a later addition. **(b)** derive macro from the start (typed, but a proc-macro crate and more P4 effort before the first release). ADR-0020 §10 (C-042). | P4 | open (C-042) |
| Q-023 | C ABI (`oec-ffi`): option style? | **(a, recommended)** builder functions and string setters (`oec_product_set(p, "SoftwareRevision", "1.2.0")`) plus JSON text for field definitions and values – small, ABI-stable without struct versioning, matches what C developers see on the bus. **(b)** option structs with a size/version member (typed, Win32 style; every new option needs a struct revision). ADR-0021 (C-042). | P4 | open (C-042) |
| Q-024 | Logger demo (D4): written in C on the C ABI? | **(a, recommended)** yes – it proves and documents the C path for the main audience (`research/sdk-options.md` §5), the logger is small and mostly a consumer; Messaging L1 stays (ADR-0016), the writable `logging` DataSet of the sketch is optional. **(b)** Rust, and the C ABI is proven only by C examples/tests. Note: ROADMAP P6 still says "configurable via the `Config` resource", ADR-0016 says file/environment – (a) keeps ADR-0016. ADR-0021 (C-042). | P4 (C ABI), P6 | open (C-042) |
| Q-025 | Micro SDK (D9): name prefix? | **(a, recommended)** `oecm_` / `OECM_` – short, no symbol clash with `oec_` of the D2 C ABI, same names after the prefix where the concept matches. **(b)** `oec_micro_` (explicit, long). **(c)** `oec_` like D2 (familiar, but clashes in one test program and hides the different ownership rules). ADR-0022 (C-042). | P4b | open (C-042) |
| Q-026 | Rust SDK (D2): which MQTT client? `rumqttc` is out: unmaintained, with the vulnerable `rustls-webpki` 0.102 in its tree (5 RustSec advisories, fix PRs closed unmerged, maintainer deprioritized it in #1029). | **(a, recommended)** own sans-IO MQTT 3.1.1 codec and session in `oec-core` + tokio TCP + rustls: the small frozen subset OEC needs, Will per connect and reconnect fully in SDK hands, no third-party code on the critical path; spike `oec/sdk/rust/spike/mqtt-codec` (307 lines, 8 byte-exact tests); P4 effort ~1–1.5k lines incl. fuzzing and broker interop tests. **(b)** fork `rumqttc-v4-next` (Apache-2.0, active, current webpki) behind an internal transport interface – fast, but one maintainer and a young API. **(c)** `paho-mqtt` (Eclipse, C library + OpenSSL; cross builds/Windows harder; EPL-2.0/EDL-1.0). ADR-0023 (C-043). Asked live in C-043; the PO was not available. | P4 | open (C-043) |
| Q-027 | Micro SDK (D9): how does the core read JSON? | **(a, recommended)** own bounded pull reader in the core: no heap, limits on depth/token length/member count, strings unescaped into caller buffers, host fuzz target; ~400–600 lines with tests. **(b)** cJSON with a static arena via `cJSON_InitHooks` (proven parser, but builds a full tree in RAM, needs an arena sized for the largest request, and is an extra managed component since ESP-IDF 6). jsmn is out (no commit since 2021, G-4.4). ADR-0024 (C-043). | P4b | open (C-043) |
| Q-028 | D7: is proxy mode required for a full level claim? Connection-level REQs (CONNECT, Will, TLS ≥ 1.2, certificate verification, authentication, no retain, recovery – T7-CON-01…04, T7-LIFE-01…03, all MUST at L1) are invisible to an ordinary bus client. | **(a, recommended)** yes: `oec-check test` without `--attach proxy` reports these tests as `skip` and the run as inconclusive (exit 4); the vendor points the CUT's Message Bus storage to D7 for a full claim – no broker-specific access needed. **(b)** also accept broker evidence (Mosquitto log/plugin) as an alternative mode (broker-specific, later). **(c)** treat these REQs as `manual` for D7 (simpler tool, weaker claim). ADR-0025, `oec/conformance/DESIGN.md` §3.4 (C-044). | P5 | open (C-044) |
| Q-029 | D7: does the tester announce itself on the bus? ADR-0025 (C-044). | P5 | open (C-044) |
| Q-030 | D7/D8: new exit code 4 "inconclusive"? | **(a, recommended)** yes: 0 pass, 1 fail, 2 usage, 3 internal, **4** no failure but a MUST test at the declared level was skipped (missing proxy/hook/docker, CUT not found, observation too short); `--allow-skip` maps 4 → 0 for partial CI runs; `validate` keeps 0–3. **(b)** skipped MUST tests count as fail (1) – mixes "violates" with "not checked". **(c)** 0 with a warning – a CI run would claim compliance it did not check. Extends the contract of ADR-0019 amendment C-040 item 7. ADR-0025 (C-044). | P5, P5b | open (C-044) |

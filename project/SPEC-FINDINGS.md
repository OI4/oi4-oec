# Spec findings – guideline v2.0 draft

Ambiguities, contradictions and gaps found in the guideline (`oi4-oec-documentation`).
**Current baseline: `49b6fe2` (branch `feature/spec-findings`, 2026-10-14)** – Messaging Guideline (MG, `docs/guideline/`) and Runtime & Infrastructure Guideline (RIG, `docs/infrastructure-guideline/`) with GL-ADR-001 … 016. The OEC Process Description (`docs/process-description/`) is informative (GL-ADR-015).

**Section numbers:** GL-ADR-015 renumbered MG chapters 7–10 to 6–9 (MQTT 6, Topics 7, Payload 8, Message Bus 9; former chapter 6 moved to the Process Description). Entries SF-001 … SF-034 cite the numbering valid when they were written (before `49b6fe2`); SF-035 and later use the current numbering.

The PO resolves findings directly in the guideline repo; the guideline repo mirrors this register in `oi4-oec-documentation/findings/SPEC-FINDINGS.md`. **SF ids are shared between both registers – the next free id is SF-039.** New findings are added here first (with location, proposed interpretation) and reported to the PO.

Each finding gets a proposed interpretation. The PO decides (ADR-0007); a decision with protocol impact also gets an ADR (ours) or a GL-ADR (guideline).

Status: `open` → `decided` (PO, cycle) → `reported` (handed to the work group) · `resolved` (fixed in the guideline) · `obsolete` (no longer applicable after a GL-ADR)

| SF-035 | Behavior stated without keyword | MG 1.2 (SF-032) makes "statements without keyword" informative. Many protocol-defining behaviors in MG 6–9 are written in plain present/future tense without a keyword (37 hits for "will publish / is published / publishes as many" alone), e.g.: `Health` is published on init, on change and every 60 s as heartbeat – no keyword anywhere (MG 7.1.5.1:20, our G-2.12); Birth "will be published whenever the connection … is established" and its topic (MG 6.3.3:8 – the level table only makes the Birth message as such mandatory); "Service A will publish an `Event`" with `Status` after `Set`/`Del` (MG 9.1.3:164, 9.1.4:154, 9.1.5:86, 9.1.8:213, 9.1.9:134/178, 9.1.10:134/202); pagination continuation "the publisher publishes as many `NetworkMessages` …" (MG 9.1.1–9.1.10); PublicationList `Mode` semantics (MG 8.3.8:82–94). | SF-036 | Closed set of resources/services | After GL-ADR-014 only the 10 resources (MG 7.1.5.1) and the common service `NewDataSetWriterId` (MG 7.1.5.2) are defined. MG 7.1.1 requires all topics below `Oi4v2` to be OI4-conform, but no sentence states whether other resource/service names (vendor Actions, own resources) are forbidden. MG 7.1.5.2 still says "For well-defined services, the service name is equal to the name of the Action" – a remnant of the removed specific services that implies other services exist. Drop or reword the "well-defined services" sentence. | decided (PO, C-013): closed set as proposed – the PO updates the guideline |
| SF-037 | Level 3 scope of methods and resources | The MG 1.3 level table row "Complete Message Bus behavior, e.g. the resources `Profile`, `PublicationList`, `SubscriptionList`, `Metadata`, `ReferenceDesignation` and `Event`" is Mandatory at Level 3, and MG 7.2 says Level 3 "supports the complete set of mandatory methods and resources defined in the following sub-chapters". But the tables in MG 7.2.1/7.2.2 list only `MAM`, `Health` (L1+), `Profile`, `PublicationList` (applications only), `ReferenceDesignation` (L2 R / L3 M); `Metadata` and `Event` are mandatory only conditionally (notes: `Data` → `Metadata`; `Set`/`Del` → `Event` category `Status`). Open: (a) are `SubscriptionList`, `Config`, `Data` and the common service `NewDataSetWriterId` required at Level 3 (MG 1.3 "e.g." list) or optional (MG 7.2.x)? (b) `Del`, `Call` and `Reply` have no level assignment at all (MG 7.2.x method tables list `Pub`, `Get`, `Set` only). (c) "Where applicable" for `Set` (L2/L3) is not in the MG 1.2 keyword mapping, and the sentence "`Set` must be supported for all resources that are offered for modification" has no level, while the table says "–" for Level 1. (d) MG 7.1.4 says a `Set`/`Del` *should* cause an `Event` `Status`, while the MG 7.2.x notes make support of `Event` with category `Status` *mandatory* when `Set`/`Del` are offered. | MG 1.3 (level table, rows 9 and 10), MG 7.2, MG 7.2.1, MG 7.2.2, MG 7.1.4 | Decided by the PO (C-015), replacing the agent's proposal ("MG 7.2.x authoritative, the rest optional"): **at Level 3 all messages are mandatory.** The "not every service is configured, subscribes or provides data" view predates the compliance levels. (a) At Level 3 an application supports all methods (`Pub`, `Get`, `Set`, `Del`, `Call`/`Reply`), all resources (`MAM`, `Health`, `Config`, `Data`, `Metadata`, `Event`, `Profile`, `PublicationList`, `SubscriptionList`, `ReferenceDesignation`) and the common service `NewDataSetWriterId`, each with the methods MG 9 defines for it; a device representation supports the resources with a `Source` of the device (all except `PublicationList`/`SubscriptionList`, which the representing application provides) – MG 7.2.1/7.2.2 list them all. Level 2: `Get` mandatory, `Set`/`Del` where applicable, the other resources and the common service recommended. **Supporting a resource does not require content:** an entity without configuration parameters, `Data` or subscriptions answers a `Get` with an empty list (`Pub` `NetworkMessage` with `"Messages": []`, the same shape the `Get` request already uses – conformant with MG 8.2.1), does not publish the resource on its own as long as it has no content, and answers a `Set`/`Del` on an object it does not have or does not offer for modification with an `Event` `Status`/`Bad`. (b) `Del`, `Call`/`Reply` get rows in the method tables (L3 mandatory). (c) "Where applicable" (Level 2) = mandatory for every resource the entity offers for modification by other participants, otherwise not required; defined in MG 7.2. (d) Every `Set`/`Del` is answered with an `Event` of category `Status` (MG 7.1.4 "should" → "must", in line with MG 8.3.6.1 "must be used to respond to modification requests"). Catalog: REQ-CMP-010, -015 … -023 reworked accordingly. | decided (PO, C-015) |
| SF-038 | Level 2 description vs. Service Container table | MG 1.3 describes Level 2 as adding "a runtime baseline consisting of the deployment as OCI-compliant container and the provision of software license information", which implies OCI deployment is not required at Level 1. RIG 1.2 (the defining document for the OEC Service Container Compliance) makes "Packaging and deployment as an OCI-compliant container" Mandatory at Level 1 and only the SBOM starts at Level 2. | MG 1.3 (Compliance Levels, Level 2 bullet), RIG 1.2 (table row 1) | Decided by the PO (C-015): **the two compliance domains are independent.** OEC Messaging Compliance is defined by the MG only, OEC Service Container Compliance by the RIG only; the level reached in one domain neither requires nor implies a level in the other. Example: a microcontroller-based smart device can reach Messaging Level 3; it is not a container, so the Service Container Compliance is not applicable (not even Level 1) – that is fine. Vice versa, a containerized application can reach Service Container Level 3 with Messaging Level 1 only. Consequences: MG 1.3 describes the levels domain-neutrally and only grades messaging requirements (the Level 2 bullet loses the OCI/SBOM runtime baseline); RIG 1.2 is the only source of the container levels (OCI from Level 1, SBOM from Level 2); RIG 5.2 lists only container/platform requirements and refers to the MG for messaging. Catalog: REQ-CMP-027/028 follow RIG 1.2; a new CMP entry states the independence. | decided (PO, C-015) |

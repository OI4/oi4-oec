# ADR-0021 – C ABI of the Rust SDK (`oec-ffi`)

- Status: **accepted** (PO, C-045 review 2026-10-26; proposed in C-042)
- Date: 2026-10-26
- Deciders: product owner (Thomas) – proposed by the agent in C-042
- Related: ADR-0011 (S4: Rust core + C ABI), ADR-0020 (Rust API), ADR-0022 (D9 API), ADR-0016 (logger demo L1), Q-023, Q-024

## PO decision (C-045 review, 2026-10-26)

Accepted as proposed. Q-023 (a): opaque builder handles with string setters and JSON for values; option structs are not used. Q-024 (a): the logger demo D4 is written in C on this ABI, Messaging Level 1, configured by file/environment (ADR-0016); the writable DataSet of the sketch stays optional.

## Context

ADR-0011 decided that D2 offers a stable C ABI (`oec-ffi`, header generated by cbindgen), so that C/C++ applications and later bindings can use the SDK. The research recommendation (`research/sdk-options.md` §5) was to prove the C path with the logger demo. P3 has to fix the ABI contract: ownership, errors, callbacks, threading and versioning.

The contract was written as a **compile-checked header** `oec/sdk/rust/sketch/c/include/oec.h` with the examples `hello.c` and `logger.c`. `oec/sdk/check.sh` compiles them as C17 with `-Wall -Wextra -Wpedantic -Werror`.

## Decision

1. **The header sketch is the ABI contract for P4.** In P4 cbindgen generates `oec.h` from `oec-ffi`. The generated header must keep the names, signatures and the contract comment of the sketch. Additions are allowed. Changes need an amendment of this ADR.
2. **Naming:** prefix `oec_` for functions and types, `OEC_` for constants. Enums with fixed values. No Rust types in the ABI.
3. **Opaque handles and ownership:**
   - `oec_*_new` / `oec_builder_build` return handles owned by the caller; `oec_*_free` releases them.
   - Child handles (`oec_asset`, `oec_dataset`, `oec_config`) belong to their `oec_app`. They are never freed individually.
   - `oec_builder_build` consumes the builder in every case, including on error. So there is no double free and no leak on the error path.
4. **Strings:**
   - NUL-terminated UTF-8.
   - Input strings are borrowed for the call; the SDK copies them.
   - Strings handed to a callback are borrowed for the callback.
   - Strings returned to the caller are owned and released with `oec_string_free`.
5. **Structured values as JSON text:**
   - field definitions (`fields_json`) and values (`values_json`, the OPC UA JSON field values of a DataSet);
   - Config definitions (the published Config DataSet, MG 8.3.3) and received payloads (`payload_json`).
   - This keeps the ABI small and stable (no struct layouts for 10 resources) and uses the format C developers see on the bus anyway. The SDK validates the JSON against the definition and reports errors with `OEC_ERR_INVALID_ARGUMENT`.
6. **Builder with setters instead of option structs:**
   - `oec_builder_*`; `oec_product_set(p, "<MAM field>", value)` with the MAM field names of MG 5.
   - New options become new functions, not new struct members. That is ABI-compatible without versioned structs.
7. **Errors:**
   - Every fallible function returns `oec_status`. `oec_last_error()` returns a message for the calling thread, valid until the next `oec_` call on that thread.
   - Rust panics never cross the ABI: they become `OEC_ERR_PANIC`, and the app is unusable afterwards.
   - Protocol results (`oec_status_code`, OPC UA StatusCode values) stay separate from API errors, as in ADR-0020 §14.
8. **Threading and callbacks:**
   - Every function may be called from any thread. Only `oec_*_free` must not run concurrently with other uses of the same handle.
   - Callbacks (`oec_set_fn`, `oec_received_fn`) run on an SDK-owned thread, one at a time per app. They may call every other `oec_` function except `oec_app_free`, and must not block for long.
   - `oec_app_run` blocks; `oec_app_start` runs on SDK threads.
   - No async in the ABI. Consumer requests (`oec_get`) block with a timeout and deliver their results through a callback before returning.
9. **Versioning:**
   - `OEC_ABI_VERSION` (compile time) and `oec_abi_version()` (run time) change on every incompatible change; `oec_version()` reports the SDK version.
   - Distribution: shared and static library per platform plus `oec.h`. The packaging is decided in P4.
10. **Behavior is the Rust behavior:** the ABI wraps ADR-0020 1:1 (level → automatic protocol, state not messages, the `Set` pipeline with automatic Status event). The ABI has no protocol logic of its own.
11. **Proof by the logger demo (D4) in C** (Q-024): `logger.c` sketches it (subscribe Event and Health, writable `logging` DataSet with a `Set` callback). This is the agent's proposal. ADR-0016 put the logger at L1 with configuration via file/environment; the writable DataSet in the sketch shows the ABI and is optional.

## Commonalities and deliberate differences with D9 (`oecm.h`, ADR-0022)

| Aspect | `oec.h` (D2 C ABI) | `oecm.h` (D9) | Why |
|---|---|---|---|
| Prefix | `oec_` | `oecm_` | Both can be linked into one test program; no symbol clash |
| Enums level/service type/health | same names and order | same names and order | Knowledge transfers; porting code is a prefix change |
| Memory | SDK allocates; opaque handles; `_free` | no heap; caller provides the device state and the tx buffer | Microcontrollers: static memory, deterministic |
| Configuration | builder with copied strings | `const` struct with borrowed strings | No heap ⇒ no copies; config lives in flash |
| Threading | any thread; callbacks on an SDK thread | single-threaded; `oecm_poll` loop; PAL events queued onto the app task | No runtime/OS assumptions in the core |
| I/O | SDK-internal (MQTT, TLS, files) | PAL function pointers (MQTT with TLS, clocks, persistence) | Portability across ESP-IDF, Arduino and other RTOSes |
| Values | JSON text | typed C values (Level 1: health only; L2/L3: fixed-size typed fields, ADR-0022) | Avoid a JSON parser on the device's hot path |
| Errors | `oec_status` + thread-local message | `oecm_err` + `oecm_err_str` (static strings) | No thread-local storage, no allocation |
| Levels | L1–L3 from the start | L1 first, L2/L3 additive (Q-019: designed for L3) | ADR-0017/0019 increments |
| Code | Rust core (`oec-core`) | separate C17 core | ADR-0017: no shared code |

## Consequences

- A new P4 increment 10 (C ABI, added to ROADMAP P4 in C-042) implements `oec-ffi` against this contract. A C test program (from `hello.c`/`logger.c`) runs in CI, also under AddressSanitizer.
- The JSON boundary costs some parsing per call. This is acceptable on edge hardware; C users with hot paths can batch values in one `oec_dataset_update`.
- If the PO prefers plain C structs (Q-023), the header grows by about 10 option structs with version fields. The JSON functions would stay for values.

## Alternatives considered

- **Option structs with a `size`/version member** (Win32 style): typed, but every option needs a new struct revision and C++ users have to zero-initialize. Kept as the fallback of Q-023.
- **Exposing the async API** (futures/polling in C): rejected, as C users expect blocking calls and callbacks.
- **Error codes only, without a message:** rejected. Messages such as "IL longer than 255 characters" are essential for DX.
- **A C API without the Rust SDK** (the D9 core also for Linux): rejected by ADR-0011/0017. D9 is designed for devices, not for the full L3 provider feature set of applications.

## Amendment C-060 (2026-10-28) – location of the contract header (agent, G-3.4 b)

Decided by the agent (layout, G-3.4 b); the PO can overrule. The Rust API sketch was deleted in C-060 (ADR-0020 amendment C-060), so the C contract moved next to the crate that will implement it: **`oec/sdk/rust/oec-ffi/include/oec.h`** with the examples **`oec/sdk/rust/oec-ffi/examples/{hello,logger}.c`** (`git mv`, content unchanged except the header comment). `oec/sdk/check.sh` compiles them there as C17 with the same flags. Decision 1 stands: the header is the ABI contract until increment 10 generates `oec.h` from `oec-ffi`; the generated header must keep its names, signatures and contract comment.

The Rust API gained `Consumer::new_data_set_writer_id` in C-060; the C contract has no counterpart yet (consumer side: `oec_get`, `oec_subscribe`). Increment 10 adds it as an addition (allowed by decision 1), with the same Target rules (ServiceType + AppId, no Filter).

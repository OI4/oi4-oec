# ADR-0021 – C ABI of the Rust SDK (`oec-ffi`)

- Status: **accepted** (PO, C-045 review 2026-10-26; proposed in C-042)
- Date: 2026-10-26
- Deciders: product owner (Thomas) – proposed by the agent in C-042
- Related: ADR-0011 (S4: Rust core + C ABI), ADR-0020 (Rust API), ADR-0022 (D9 API), ADR-0016 (logger demo L1), Q-023, Q-024

## PO decision (C-045 review, 2026-10-26)

Accepted as proposed. Q-023 (a): opaque builder handles with string setters and JSON for values; option structs are not used. Q-024 (a): the logger demo D4 is written in C on this ABI, Messaging Level 1, configured by file/environment (ADR-0016); the writable DataSet of the sketch stays optional.

## Context

ADR-0011 decided that D2 offers a stable C ABI (`oec-ffi`, header generated by cbindgen), so that C/C++ applications and later bindings can use the SDK. The research recommendation (`research/sdk-options.md` §5) was to prove the C path with the logger demo. P3 has to fix the ABI contract: ownership, errors, callbacks, threading and versioning.

The contract was written as a **compile-checked header** `oec/sdk/rust/sketch/c/include/oec.h` with the examples `hello.c` and `logger.c`. `oec/sdk/check.sh` compiles them as C17 with `-Wall -Wextra -Wpedantic -Werror`.

## Decision

1. **The header sketch is the ABI contract for P4.** In P4 cbindgen generates `oec.h` from `oec-ffi`. The generated header must keep the names, signatures and the contract comment of the sketch. Additions are allowed. Changes need an amendment of this ADR.
2. **Naming:** prefix `oec_` for functions and types, `OEC_` for constants. Enums with fixed values. No Rust types in the ABI.
3. **Opaque handles and ownership:**
   - `oec_*_new` / `oec_builder_build` return handles owned by the caller; `oec_*_free` releases them.
   - Child handles (`oec_asset`, `oec_dataset`, `oec_config`) belong to their `oec_app`. They are never freed individually.
   - `oec_builder_build` consumes the builder in every case, including on error. So there is no double free and no leak on the error path.
4. **Strings:**
   - NUL-terminated UTF-8.
   - Input strings are borrowed for the call; the SDK copies them.
   - Strings handed to a callback are borrowed for the callback.
   - Strings returned to the caller are owned and released with `oec_string_free`.
5. **Structured values as JSON text:**
   - field definitions (`fields_json`) and values (`values_json`, the OPC UA JSON field values of a DataSet);
   - Config definitions (the published Config DataSet, MG 8.3.3) and received payloads (`payload_json`).
   - This keeps the ABI small and stable (no struct layouts for 10 resources) and uses the format C developers see on the bus anyway. The SDK validates the JSON against the definition and reports errors with `OEC_ERR_INVALID_ARGUMENT`.
6. **Builder with setters instead of option structs:**
   - `oec_builder_*`; `oec_product_set(p, "<MAM field>", value)` with the MAM field names of MG 5.
   - New options become new functions, not new struct members. That is ABI-compatible without versioned structs.
7. **Errors:**
   - Every fallible function returns `oec_status`. `oec_last_error()` returns a message for the calling thread, valid until the next `oec_` call on that thread.
   - Rust panics never cross the ABI: they become `OEC_ERR_PANIC`, and the app is unusable afterwards.
   - Protocol results (`oec_status_code`, OPC UA StatusCode values) stay separate from API errors, as in ADR-0020 §14.
8. **Threading and callbacks:**
   - Every function may be called from any thread. Only `oec_*_free` must not run concurrently with other uses of the same handle.
   - Callbacks (`oec_set_fn`, `oec_received_fn`) run on an SDK-owned thread, one at a time per app. They may call every other `oec_` function except `oec_app_free`, and must not block for long.
   - `oec_app_run` blocks; `oec_app_start` runs on SDK threads.
   - No async in the ABI. Consumer requests (`oec_get`) block with a timeout and deliver their results through a callback before returning.
9. **Versioning:**
   - `OEC_ABI_VERSION` (compile time) and `oec_abi_version()` (run time) change on every incompatible change; `oec_version()` reports the SDK version.
   - Distribution: shared and static library per platform plus `oec.h`. The packaging is decided in P4.
10. **Behavior is the Rust behavior:** the ABI wraps ADR-0020 1:1 (level → automatic protocol, state not messages, the `Set` pipeline with automatic Status event). The ABI has no protocol logic of its own.
11. **Proof by the logger demo (D4) in C** (Q-024): `logger.c` sketches it (subscribe Event and Health, writable `logging` DataSet with a `Set` callback). This is the agent's proposal. ADR-0016 put the logger at L1 with configuration via file/environment; the writable DataSet in the sketch shows the ABI and is optional.

## Commonalities and deliberate differences with D9 (`oecm.h`, ADR-0022)

| Aspect | `oec.h` (D2 C ABI) | `oecm.h` (D9) | Why |
|---|---|---|---|
| Prefix | `oec_` | `oecm_` | Both can be linked into one test program; no symbol clash |
| Enums level/service type/health | same names and order | same names and order | Knowledge transfers; porting code is a prefix change |
| Memory | SDK allocates; opaque handles; `_free` | no heap; caller provides the device state and the tx buffer | Microcontrollers: static memory, deterministic |
| Configuration | builder with copied strings | `const` struct with borrowed strings | No heap ⇒ no copies; config lives in flash |
| Threading | any thread; callbacks on an SDK thread | single-threaded; `oecm_poll` loop; PAL events queued onto the app task | No runtime/OS assumptions in the core |
| I/O | SDK-internal (MQTT, TLS, files) | PAL function pointers (MQTT with TLS, clocks, persistence) | Portability across ESP-IDF, Arduino and other RTOSes |
| Values | JSON text | typed C values (Level 1: health only; L2/L3: fixed-size typed fields, ADR-0022) | Avoid a JSON parser on the device's hot path |
| Errors | `oec_status` + thread-local message | `oecm_err` + `oecm_err_str` (static strings) | No thread-local storage, no allocation |
| Levels | L1–L3 from the start | L1 first, L2/L3 additive (Q-019: designed for L3) | ADR-0017/0019 increments |
| Code | Rust core (`oec-core`) | separate C17 core | ADR-0017: no shared code |

## Consequences

- A new P4 increment 10 (C ABI, added to ROADMAP P4 in C-042) implements `oec-ffi` against this contract. A C test program (from `hello.c`/`logger.c`) runs in CI, also under AddressSanitizer.
- The JSON boundary costs some parsing per call. This is acceptable on edge hardware; C users with hot paths can batch values in one `oec_dataset_update`.
- If the PO prefers plain C structs (Q-023), the header grows by about 10 option structs with version fields. The JSON functions would stay for values.

## Alternatives considered

- **Option structs with a `size`/version member** (Win32 style): typed, but every option needs a new struct revision and C++ users have to zero-initialize. Kept as the fallback of Q-023.
- **Exposing the async API** (futures/polling in C): rejected, as C users expect blocking calls and callbacks.
- **Error codes only, without a message:** rejected. Messages such as "IL longer than 255 characters" are essential for DX.
- **A C API without the Rust SDK** (the D9 core also for Linux): rejected by ADR-0011/0017. D9 is designed for devices, not for the full L3 provider feature set of applications.

## Amendment C-061 (2026-10-28) – increment 10: the generated ABI and its deviations from the contract (agent, G-3.4 b)

Decided by the agent within this ADR (APIs within an accepted ADR, build and test setup, G-3.4 b); the PO can overrule. Details: `log/2026-10-28_C-061_oec-ffi.md`, REVIEW A-145 … A-152. Additive `oec` API for the ABI: ADR-0020 amendment C-061; workspace, lints and tests: ADR-0026 §20; tool and dependencies: ADR-0023 amendment C-061.

**Implementation.** Crate `oec/sdk/rust/oec-ffi` (`cdylib` + `staticlib` + `rlib`) on `oec`; modules `abi` (status, last error, panic guard, callback guard, strings), `types` (protocol constants), `app` (product, builder, app), `asset` (assets, DataSets, Config, events), `consumer` (subscriptions, `Get`/`Set`/`Del`, the Action). `include/oec.h` is generated by **cbindgen 0.29.4** from the crate (`cbindgen.toml` holds the contract comment of the header), committed, and compared with a fresh output by `oec/sdk/check.sh` (decision 1). The ABI keeps every name of the P3 contract except one (5.), and its rules on ownership, strings, JSON values, builders and panics (decisions 2 … 7, 10).

**Deviations from the P3 contract** (decision 1 asks for an amendment):

1. **Constants instead of C enums.** `oec_level`, `oec_service_type`, `oec_health`, `oec_resource`, `oec_writable`, `oec_syslog_level` and `oec_status` are `int32_t` typedefs with `#define` constants of the same names and values. A C enum value outside the declared range would be undefined behavior on the Rust side; as integers, out-of-range values are refused with `OEC_ERR_INVALID_ARGUMENT`. C source using the names compiles unchanged.
2. **ServiceType in requests and subscriptions.** `oec_subscribe` and `oec_get` (and the new `oec_set`, `oec_del`, `oec_new_data_set_writer_id`) take an `oec_service_type service_type` before `app_il`; `OEC_ST_ANY` (−1) is the wildcard of a subscription. A request needs a concrete ServiceType and AppId (ADR-0020 amendment C-058 C.3: no broadcast `Get`); a Filter needs a Source (topic rules); `OEC_ST_ANY` or a NULL `app_il` in a request → `OEC_ERR_INVALID_ARGUMENT`.
3. **Generic event level.** `oec_asset_emit_event(asset, level, number, description, details_json)`: the Generic event topic carries a level (`Pub/Event/<Source>/Generic/<level>`, REQ-RES-EVENT-009; ADR-0026 §16), so the C call names it like `Asset::emit_event`.
4. **Errors.** `oec_last_error()` is set only when a call fails and stays valid until the next failing `oec_` call on that thread (not "until the next call": a successful call does not overwrite it). New `OEC_ERR_NOT_CONNECTED` (8, a request while offline, `oec::Error::NotConnected`) and `OEC_ERR_STATUS` (9, the responder answered with a Bad StatusCode, `oec::Error::Status`) with `oec_last_status_code()` for that code.
5. **`oec_dataset_set_precision` removed.** The Precision is a member of the field definition in `fields_json` (`"Precision": 0.5`), as `DataSetDef`/`Publication::precision` in Rust fixes it when the DataSet is added; a later change is a `Set PublicationList` (ADR-0026 §14).
6. **Callbacks.** They run on the thread that runs the app – the caller of `oec_app_run` or the SDK thread of `oec_app_start` – one at a time per app; the callbacks of `oec_get` run on its caller's thread before it returns. Inside a callback the blocking functions (`oec_get`, `oec_set`, `oec_del`, `oec_new_data_set_writer_id`, `oec_app_run`) and `oec_app_free` are refused with `OEC_ERR_INVALID_STATE`: they would wait for the thread that is running the callback (contract: "every other function except `oec_app_free`"). Every other function may be called, including `oec_subscription_free` of the own subscription. The `oec_set_fn` parameter is named `json` (it receives Data values and Config values).
7. **Child handles** stay valid until their app is freed, also after `oec_asset_remove`/`oec_dataset_remove` (their calls then fail with `OEC_ERR_INVALID_ARGUMENT`, as in Rust); this makes a use after remove an error instead of undefined behavior.
8. **`oec_app_start`** runs the app on an SDK thread (own `current_thread` tokio runtime, no signal handling, like `App::run_async`); an error of that thread (e.g. the bootstrap fails at the first connect) ends it and is not reported back – the app stays offline and requests fail with `OEC_ERR_NOT_CONNECTED`. `oec_app_run` reports it.
9. **Panics** (decision 7): every exported function runs inside `catch_unwind`; a panic → `OEC_ERR_PANIC` and the app is marked unusable (every later call on it → `OEC_ERR_PANIC`); a panic inside a callback wrapper is caught as well.

**Additions** (allowed by decision 1): `oec_set`, `oec_del` (only the allowed combinations: ReferenceDesignation, SubscriptionList; others → `OEC_ERR_INVALID_ARGUMENT`), `oec_new_data_set_writer_id` (amendment C-060; Target rules: ServiceType + AppId, optional Source, no Filter), `oec_dataset_remove`, `oec_config_set` (the application changes a Config value: the checks of a `Set Config`, persisted and published, no Status event, no `on_set` call), `oec_builder_free` (a builder that is not built), `oec_last_status_code`, StatusCode constants `OEC_BAD_INVALID_ARGUMENT`, `OEC_BAD_USER_ACCESS_DENIED`, `OEC_BAD_INTERNAL_ERROR`.

**Not exposed in C (yet)** – Rust API items without a C function; additive later, none is needed by the logger demo (P6): `on_presence`/`apps`, `Subscription::configurable`/`interval`, `HealthDetail`, ReferenceDesignation handlers, `bump_revision_counter`, DataSet ClassId/description, `on_connection`/`ConnectionState`, ClientId/keep alive/MaxPacketSize options of the builder, `run_async`.

**Packaging** (decision 9, "decided in P4"): per platform `liboec_ffi.{so,dylib}` / `oec_ffi.dll` + import library, `liboec_ffi.a` (`oec_ffi.lib` with MSVC) and `include/oec.h`; static linking needs the system libraries of `rustc --print native-static-libs` (macOS: `-liconv -lSystem -lc -lm`; Linux glibc: `-lgcc_s -lutil -lrt -lpthread -lm -ldl -lc`). `OEC_ABI_VERSION` is 1. Release archives and a pkg-config file come with P9.

**Tests** (Consequences: "runs in CI, also under AddressSanitizer"): Rust unit tests of the FFI layer without network; `tests/c.rs` compiles `examples/hello.c`, `examples/logger.c` and the ABI test program `tests/c/abi.c` as C17 with `-Werror` against the shared library and against the static library with `-fsanitize=address,undefined` and runs them against the in-process TLS test broker (`oec/sdk/check.sh` requires the sanitizers); on Linux LeakSanitizer runs too.

## Amendment C-076 (2026-11-01) – `oec_app_state` and `oec_app_wait` for the Go SDK (agent, G-3.4 b)

Additive extension, allowed by the PO order of 2026-11-01 (P4c: "Erweiterungen von `oec`/`oec-ffi`, die nichts Bestehendes brechen"); needed by the Go SDK (ADR-0027 amendment C-076). Details: `log/2026-11-01_C-076_go-sdk-core.md`, REVIEW A-312, A-313. ABI version stays 1; no existing signature, behavior or test changes.

1. **Spike finding of C-075 explained (test first, `tests/c/abi.c` `lifecycle`).** A MAM subscription of an app started with `oec_app_start` receives the Birth of a peer that connects later and the own MAM as answer of a `Get`, but never its own Birth: the runtime sends the SUBSCRIBE of consumer subscriptions after the Birth (the Birth is the first message, REQ-LIFE-015), and MAM is not retained. This is intended behavior, not a defect. In the spike no peer connected during the 15 s.
2. **§8 revised: start errors are observable.** `oec_app_wait(app, timeout_ms)` waits until the run of `oec_app_start` has ended and returns its result every time it is asked: `OEC_OK` after `oec_app_shutdown`, otherwise the start error (`OEC_ERR_BOOTSTRAP` for unusable TLS material, `OEC_ERR_INVALID_ARGUMENT`, `OEC_ERR_IO`) with its `oec_last_error`; `OEC_ERR_TIMEOUT` while the app still runs (`timeout_ms` 0 = only look, `OEC_WAIT_FOREVER` = no limit); `OEC_ERR_INVALID_STATE` without `oec_app_start` and inside a callback (it blocks). A panic on the SDK thread is `OEC_ERR_PANIC` and marks the app unusable (before, the thread ended silently). `oec_app_start` itself is unchanged (it still returns `OEC_OK` before the connection).
3. **`oec_app_state(app, &state)`** gives the connection state of `AppHandle::state` as `oec_connection_state` (`int32_t`, constants as in deviation 1): `OEC_STATE_CONNECTING` 0, `OEC_STATE_ONLINE` 1, `OEC_STATE_RECONNECTING` 2, `OEC_STATE_CLOSED` 3 (also before the run and after a start error). Allowed inside a callback. This covers the item "`on_connection`/state" of "Not exposed in C (yet)" as a query (no callback).
4. **Why the Go SDK needs them.** Go's `App.Run(ctx)` cannot use `oec_app_run`: its SIGINT/SIGTERM handlers (tokio) are installed without `SA_ONSTACK`, which the Go runtime requires of non-Go signal handlers (`os/signal` documentation, "Go programs that use cgo"), and they would take the signals from the Go program. The Go package uses `oec_app_start` + `oec_app_wait` instead and leaves the signals to Go (`signal.NotifyContext`).
5. **Header:** 45 functions; the cbindgen rename `ConnectionState` → `oec_connection_state`. The gate diffs the header as before.

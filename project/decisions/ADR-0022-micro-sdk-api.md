# ADR-0022 – API of the micro SDK (D9)

- Status: **accepted** (PO, C-045 review 2026-10-26; proposed in C-042)
- Date: 2026-10-26
- Deciders: product owner (Thomas) – proposed by the agent in C-042
- Related: ADR-0016 (micro SDK, levels; amendment C-016 / Q-019: designed for L3), ADR-0017 (C17, PAL, ESP32/ESP-IDF, Arduino, M5Stack), ADR-0021 (C ABI of D2), Q-025, SF-102

## PO decision (C-045 review, 2026-10-26)

Accepted as proposed. Q-025 (a): prefix `oecm_` / `OECM_`. SF-102 decided as proposed: a directly connected smart device uses the `ServiceType` `OTConnector` (MG 7.2); its `DeviceClass` is the product class (REQ-RES-MAM-014 applies to applications). `OTConnector` is therefore the specified value, not only the example default.

## Context

ADR-0017 fixed language (C17), structure (portable core + PAL) and the reference port (ESP-IDF on ESP32). It says the API "follows the C API of D2 where sensible", without sharing code. Q-019 decided that D9 is designed for Messaging Level 3, delivered from Level 1 on. P3 has to sketch the API (ROADMAP P3, item 3).

The sketch is the **compile-checked header** `oec/sdk/micro/sketch/include/oecm.h` with the example `examples/hello_device.c` (stub PAL). `oec/sdk/check.sh` compiles it as C17 with `-Wall -Wextra -Wpedantic -Werror`.

## Decision

1. **The header sketch is the API contract for P4b increment 1 (Level 1).** Changes need an amendment. Level 2/3 functions are additions (point 9).
2. **Prefix `oecm_` / `OECM_`** (Q-025):
   - same names as `oec.h` where the concept matches (level, service type, health, error categories);
   - same enum order, so porting between D2 C and D9 is a prefix change;
   - no shared code and no shared header (ADR-0017).
3. **No heap:**
   - the caller provides the device state (`oecm_device`, opaque, `OECM_DEVICE_SIZE` bytes, max-aligned) and the transmit buffer (≥ `OECM_TX_MIN`);
   - the core never calls `malloc`;
   - the size constants are measured and fixed in P4b and checked by a static assertion in the core.
4. **Borrowed `const` configuration** (`oecm_config` with the `oecm_mam`):
   - all strings stay valid while the device is in use (string literals or static buffers in flash); the core copies nothing;
   - `oecm_init` validates the IL (REQ-IL-008/016/019), the level and the buffer sizes;
   - with `identification_link` = NULL the core builds the Oi4Identifier from the MAM (REQ-IL-007, REQ-RES-MAM-006).
5. **Single-threaded event model:**
   - every `oecm_` function, including the `oecm_on_*` entry points of the PAL, runs on one task;
   - `oecm_poll()` drives timers (Health heartbeat REQ-TOP-017, reconnect backoff); `oecm_poll_interval_ms()` reports the latest next call;
   - a port whose MQTT client delivers events on another task (esp-mqtt) queues them onto the application task;
   - so the core needs no locks and no RTOS.
6. **PAL as a struct of function pointers with `ctx`:**
   - MQTT 3.1.1 connect, publish, subscribe and disconnect;
   - Unix and monotonic clocks;
   - optional persistence.
   - **TLS is the duty of the PAL:** always TLS ≥ 1.2 with broker certificate verification and authentication (REQ-MQTT-005/008/009). The API has no plain connection.
   - Optional functions are NULL: `mqtt_subscribe` at Level 1; persistence without Level 3 ReferenceDesignation/Config.
7. **Will per connect** (REQ-LIFE-008/016):
   - the core creates a new Will (MessageId with the creation time) for every connect and hands it over in `oecm_connect`;
   - **port consequence:** the automatic reconnect of esp-mqtt reuses the configured Last Will. So the ESP-IDF port disables it (`disable_auto_reconnect`), and the core reconnects through `mqtt_connect` with a new Will.
8. **A wall clock is mandatory** (MessageId, Timestamp; REQ-MSG-007):
   - `oecm_start` fails with `OECM_E_STATE` while `unix_time_ms` returns no plausible time;
   - the ESP-IDF example uses SNTP.
9. **Level 2/3 as additions** (designed now, implemented in later P4b increments):
   - Data: `oecm_data_def` with a fixed field array of typed C values (`OECM_DOUBLE`, `OECM_INT32`, `OECM_BOOL`, `OECM_STRING` with capacity), `oecm_add_data(dev, &def, storage)` with caller-provided storage, `oecm_data_update(dev, idx)` after the application changed the values;
   - `Get`/pagination are handled in the core from the tx buffer (a message larger than the buffer is paginated, REQ-PAG-005);
   - `Set`: `oecm_on_set` callback with typed values, returning an `oecm_status_code` (same OPC UA values as `oec.h`); the core sends the Status event (REQ-RES-EVENT-005);
   - lists (Profile, PublicationList, SubscriptionList, ReferenceDesignation) and `NewDataSetWriterId` are generated by the core from the static definitions;
   - Config: a static array of `oecm_config_object` with typed storage.
   - The level is in `oecm_config` from the start; calls above it fail with `OECM_E_LEVEL`.
10. **Identity defaults for a device:**
    - `HardwareRevision`/`SoftwareRevision` `"undefined"` when unknown (physical asset, REQ-RES-MAM-008/010);
    - `SerialNumber`, e.g. from the MAC address (REQ-RES-MAM-015);
    - `ClientId` derived from the IL and stable across reconnects (REQ-MQTT-013);
    - **ServiceType** `OTConnector` in the example, until SF-102 is decided. `DeviceClass` is the product class, not `Oi4.<ServiceType>` (REQ-RES-MAM-014 applies to applications).
11. **Errors:** `oecm_err` with `oecm_err_str` (static strings; no thread-local storage, no allocation).

The commonalities with and deliberate differences from `oec.h` are listed in ADR-0021.

## Consequences

- P4b increment 1 implements this header with:
  - host unit tests (CMake + Unity, test vectors of `oec/spec`);
  - the ESP-IDF port (esp-mqtt, esp-tls/mbedTLS, SNTP, NVS for persistence);
  - the M5Stack example.
- The PAL makes the Arduino port (ADR-0017 amendment C-010) a second PAL implementation on top of an Arduino MQTT client. That client must support TLS and a Will per connect (checked in C-043, ADR-0024: the Arduino port reuses the ESP-IDF PAL on esp-mqtt from the Arduino-ESP32 core; fallback arduino-mqtt).
- The fixed `OECM_DEVICE_SIZE` is a compile-time ABI constant. A core that needs more state fails the static assertion and the constant grows (minor version).

## Alternatives considered

- **Same prefix `oec_` as D2:** maximum familiarity, but a symbol clash when both are linked into one host test program, and the different ownership rules would confuse. Rejected; the alternative `oec_micro_` is long (Q-025).
- **Heap with a pluggable allocator:** simpler API (copies of strings), but non-deterministic memory on MCUs. Rejected.
- **Callback-driven core on the MQTT task (no `poll`):** fewer lines in the example, but locks or races in the core and an RTOS dependency. Rejected.
- **JSON values at the API (as `oec.h`):** uniform with D2, but needs a JSON parser on the hot path and dynamic sizes. Rejected for values; JSON stays internal.

## Amendment C-092 (2026-11-08) – P4b increment 1: Level 1 core (agent, G-3.4 b)

The sketch became the real header `oec/sdk/micro/include/oecm.h` (the folder `sketch/` is removed); the implementation decisions are in ADR-0030. Details: `log/2026-11-08_C-092_micro-core-l1.md`, REVIEW A-429 … A-438. Changes to the contract of §1 … §11:

1. **`oecm_mam.global_asset_id`** (A-430): optional AAS globalAssetId, appended after `revision_counter` (REQ-RES-MAM-023); `NULL` omits `GlobalAssetId`, as `NULL` omits `Description`. `NULL` hardware or software revision is sent as `"undefined"` (§10), every other `NULL` text as `""`.
2. **ClientId** (A-430, §10): without `client_id` the core derives `oec` + 16 lower-case hex digits of the FNV-1a 64 hash of the Identification Link (19 characters; stable across reconnects and restarts, REQ-MQTT-013). A given `client_id` has 1 … 23 octets.
3. **`oecm_init`** (A-431): checks UTF-8 of every text, the ManufacturerUri (REQ-RES-MAM-004), the Identification Link or the built Oi4Identifier, `revision_counter ≥ -1` and the PAL functions of Level 1; it encodes the Birth once with the longest possible MessageId and returns `OECM_E_NOSPACE` if it does not fit. Level 2 and 3 return `OECM_E_LEVEL` until their increment is delivered (C-094, C-095). `oecm_start` returns `OECM_E_STATE` while the wall clock is before 2020-01-01 (no SNTP yet).
4. **Timers** (A-432): reconnect after 1 s, doubling up to 30 s, reset by a successful connect; a connect without `oecm_on_connected` is given up after 30 s (PAL `mqtt_disconnect`, then backoff); `oecm_poll_interval_ms` returns at most 1000. A failed publication stays due and is retried by the next `oecm_poll`.
5. **Health** (A-432): `oecm_set_health` rejects `NORMAL`/0 (`OECM_E_ARG`): it is the Close (REQ-LIFE-005). After an own `FAILURE`/0 the next other Health is preceded by a Birth (REQ-LIFE-017), as in `oec-core`.
6. **Sizes** (A-433, §3): `OECM_DEVICE_SIZE` stays **1024** (Level 1 uses 368 octets on a 64-bit host; the rest is reserved for Level 2/3). `OECM_TX_MIN` stays **2048**: every Health, Will and Close fits also with a 255-octet Identification Link (1804 octets); the Birth is checked by `oecm_init` (typical about 1000 octets, 2315 with a 255-octet Identification Link and empty texts).
7. **Messages** (A-434): as `oec-core`: DataSetWriterId 10 (MAM) and 11 (Health) (ADR-0030 §9), DataSetWriterName the Identification Link, `WriterGroupName` and `ReplyTo` empty, no Timestamp, no SequenceNumber.

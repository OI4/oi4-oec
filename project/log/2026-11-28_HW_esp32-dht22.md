## 1. Setup

| Item | Value |
|---|---|
| Board | AZ-Delivery ESP32-WROOM-32 DevKit, ESP32-D0WDQ6 rev 1.0, 4 MB flash, USB serial `/dev/cu.usbserial-0001` |
| Sensor | DHT22 (AM2302) on GPIO 23 |
| Network | Wi-Fi 2.4 GHz, WPA3-SAE (H2E), RSSI −65 dBm; board 192.168.178.106, Mac 192.168.178.53 |
| Firmware | ESP-IDF 6.1, `examples/esp-idf` (C-096) copied to `/tmp/oec-hw/fw`, Level 3 |
| Broker | own Mosquitto from a copy of `oec/dev/compose.yaml` (project `oec-hw`, PKI `go run ./pki -out … -san 192.168.178.53`), bound to 192.168.178.53:8883 – the `oec/dev` stack of the other session was not touched |
| D7 | `oec-check` built from `oec/conformance` at `ef12881` |

**Local variant (not in the repo).** `main/oecm_sensor_dht22.c` replaces
`examples/sensor/oecm_sensor.c` behind the same header: Data `Climate`
(Temperature °C, Humidity %, Label; read-only, 60 s periodic), Config
`Sensor` (Interval 2 … 3600 s, default 10; Label). The DHT22 is read
bit-banged in a task on core 1 (critical section ~5 ms, three attempts,
checksum and range check); three failed rounds set Health `FAILURE_1`, the
next good reading `NORMAL_0`/100. `main.c` changes only Model/ProductCode
(`OEC Micro ESP32 DHT22`, `OECM-ESP32-DHT22`) and starts the DHT task.

Identification Link:
`oi4.org/OEC,20Micro,20ESP32,20DHT22/OECM-ESP32-DHT22/3C6105316C8C`
(serial = base MAC), ServiceType `OTConnector`.

## 2. Results

- **DHT22 alone** (no provisioning): stable readings, e.g. 23.1 °C / 45.5 %.
- **Direct to the broker:** Wi-Fi up after ~2 s, SNTP, device started ~5 s
  after boot. Heap free 158 492 octets at start, minimum 121 264 after
  the TLS connect; main stack unused 5 964 octets.
- **D7 `monitor`** (130 s, Level 3, with a reset during the run): 14 pass,
  0 fail, 1 info, 4 skip – INCONCLUSIVE (exit 4) as expected for a passive run.
- **D7 `test` Level 3** through the proxy (`--proxy-listen 127.0.0.1:18883
  --proxy-name 192.168.178.53`), restart hook (`stop` over the serial console,
  reset via RTS), `--peer --announce`: **47 pass, 0 fail, 1 info, 7 skip;
  result PASS (exit 0)**, run 10:16:46 … 10:18:23 UTC (97 s). All T7-CON-01 … 04
  and T7-LIFE-01 … 04 pass; the board refused TLS 1.1, the untrusted CA and
  the wrong host name; `restore`: state after the write tests equals the
  state before.
  - Skips, all "not applicable": T7-MON-07, T7-MON-17 (nothing observed),
    T7-ADR-01 (the board sends no requests), T7-ADR-02 (one namespace),
    T7-SET-04, T7-SET-10 (no ReferenceDesignation object), T7-SET-12 (no Syslog).
  - Info T7-MON-03: a Health `FAILURE_1`/0 without an observed Birth – the
    Will of the previous connection, published by the broker after flashing
    the provisioning had reset the board.
- **Bus values** (capture): `Climate` with Temperature 23.0 … 23.2 °C,
  Humidity 45.3 … 45.8 %.

**Found and fixed in the local variant (no SDK defect):** the first `Climate`
publication after a boot carried 0.0/0.0, because the DHT task had not read
yet. The variant now takes the first reading in `oecm_sensor_setup` (waits up
to 5 s). The repo example starts with 21.0 °C and is not affected; whoever
copies the pattern for a real sensor should do the same.

## 3. How it was run (for a repeat)

- Serial daemon (pyserial of the ESP-IDF Python env) holds the port, logs
  the console and executes lines of a FIFO (`reset` pulses RTS, others go to
  the console) – the hooks need the port while it is open.
- macOS firewall: the proxy listens on loopback; a TCP forwarder container
  (static Go binary, mounted into the pinned Mosquitto image) publishes
  `192.168.178.53:18883` → `host.docker.internal:18883`.
- Provisioning per run: `oecprov` with `uri`, `ca` (broker CA or proxy CA),
  dev app credentials, `level` 3, Wi-Fi; CSV removed right after generating
  the image.
- The README section "Run on real hardware" records the result and these
  two points; the Community page `micro-sdk` updates its limit.

## 6. Addendum: on the `oec/dev` broker (PO question "Können wir den von oec-dev auch verwenden?")

Asking the PO was not possible, so the agent chose the variant that leaves the
running `oec/dev` stack (another session) untouched: no re-keying, no restart,
no compose change.

- **Name check:** the `oec/dev` broker certificate names `localhost`,
  `mosquitto`, `127.0.0.1` and `::1`, but not the LAN IP. The board reaches
  the broker through a forwarder on the LAN IP and verifies the CA and the
  name `mosquitto`. One local line in a copy of the PAL in `/tmp` sets
  `c.broker.verification.common_name = "mosquitto"`. The repo PAL is
  unchanged. A permanent alternative is to issue the dev certificate with
  the LAN IP (`go run ./pki -san …` and `OEC_DEV_BIND`); that was not done
  because it re-keys the shared stack.
- **Forwarder:** container `oec-hw-fwd-8883`
  (`192.168.178.53:8883` → `host.docker.internal:8883`, `--restart
  unless-stopped`, static `fwd` binary from the session folder mounted into
  the pinned Mosquitto image). The board uses the `oec-dev-app` credentials
  and the `oec/dev` CA.
- **Registry:** `GET https://localhost:5799/api/assets` lists
  `…/OECM-ESP32-DHT22/3C6105316C8C`: online, `NORMAL_0`/100, MAM
  "OEC Micro ESP32 DHT22", 0 violations in 243 messages.
- **D7 `test`, level 3, against `mqtts://localhost:8883` (`oec/dev`)** through
  the proxy (`--proxy-name mosquitto,192.168.178.53`, restart hook,
  `--peer`, `--announce`):
  - Run 1: 45 pass, **1 fail**, 1 info, 8 skip. T7-LIFE-01 / REQ-LIFE-016:
    on relay connection 1, the Will's MessageId was created 7.1 s before
    the CONNECT (tolerance 5 s).
  - Run 2: **48 pass, 0 fail, 7 skip, PASS** (exit 0).
- **Analysis of the run 1 fail (no SDK defect found):**
  - The core builds a new Will on every `connect()`
    (`src/oecm_device.c`, REQ-LIFE-008/016).
  - The PAL hands it to esp-mqtt on every attempt (`esp_mqtt_set_config`).
    `esp_mqtt_client_reconnect` (auto reconnect is off) connects at once,
    without a wait.
  - In run 1 the provisioning flash reset the board, and then the run
    script reset it again. The first boot left a dangling TLS handshake
    (connection 0, proxy timeout after 10 s).
  - After the second boot, 4.9 s passed between `connect()` (Will
    timestamp) and the forwarder's accept, and another 2.2 s until the
    CONNECT. The likely cause is a slow first TCP setup right after Wi-Fi
    association (the time sync of that boot also needed three tries).
  - The Will is built in the core before the network connect. A delay in
    TCP and TLS setup therefore ages it. Building it inside the CONNECT is
    not possible with esp-mqtt, whose Will is part of the client config.
  - The local `prov.sh` now flashes the NVS with `--after no-reset`, so
    only the run script resets the board. Run 2 passed this way.
  - If the delay shows up again on real networks, this is a candidate
    finding for the 5 s tolerance or the PAL. It stays as an observation
    here; no change without a PO order.

**Still running (on purpose):** container `oec-hw-fwd-8883` and the board
connected to `oec/dev`. The D7 forwarder `oec-hw-fwd-18883` and the serial
daemon are removed. `/tmp/oec-hw` (firmware, build, PAL copy, proxy CA,
captures) is still there for repeats. To end the setup:

    docker rm -f oec-hw-fwd-8883
    rm -rf /tmp/oec-hw
    python -m esptool -p /dev/cu.usbserial-0001 erase-flash   # removes firmware, Wi-Fi and credentials

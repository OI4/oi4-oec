## Addendum 1 – PO question on D-4, delegation of engineering decisions (2026-10-26)

### PO input

1. Question on D-4: can a receiver tell, with the optional masking, whether a value is masked or natively contains the characters?
2. Instruction: the agent decides questions like D-1 (Rust programming, structure, …) itself and asks the PO on contradictions or missing definitions in the guideline.

### Answer to the question → SF-104

- A receiver cannot tell. There is no marker, and the mask sign `,` is permitted in an Identification Link (MG 4.1), so `A,2F3` is either native or a masked `A/3`.
- Receivers are not affected: MG 4.1 forbids decoding an IL; it is compared as an opaque string.
- The generator side is: with optional masking the same nameplate can give two Oi4Identifiers (`ABC@home` / `ABC,40home`), against the regeneration promise of MG 4.3. MG 4.3.1 ("mask these characters") and MG A3 Table 19 (whole element) also differ on the scope.
- This is a gap in the guideline with protocol impact, so it is a PO decision (G-3.4 a, G-3.5). Registered as **SF-104** (open) in the guideline repo, register-only commit `c41b59a`, no re-baseline (baseline stays `e0262dd`). Options: (a) always dnp-encode Model, ProductCode and SerialNumber (recommended), (b) encode a whole element only when needed, (c) keep "may".
- The PO was asked in the session and was not available, so SF-104 stays open as the only PO decision (REVIEW D-1). No code change is needed now: `oec-core` already supports both (`.dnp_encoded()` opt-in); the builder doc and ADR-0026 §5.2 cite SF-104 (G-3.5). C-047 does not depend on it.

- PO follow-up: "is it about the payload rather than the topic, mainly `"`?" – Answer: both alike. base64url (MG 4.2) and JSON escaping are lossless; the ambiguity is in building the IL string, so the variants differ in topic (Source, Filter) and payload (`ProductInstanceUri`, registry). `"` is not permitted in an IL (MG 4.1) and must be masked anyway; the free choice concerns only the reserved characters other than `/`. While checking, MG 4.1 turned out to say such values "must be masked by other means" – a second contradiction with "may" in MG 4.3.1/A3. Added to SF-104 as (4), register commit `4b4a5c8`.

## Addendum 2 – SF-104 decided by the PO (2026-10-26)

### PO input

"MG 4.1 is leading and unambiguous here: Since the percent sign % is not permitted, percent-encoding according to RFC 3986 cannot be used within an Identification Link. If values (e.g. a serial number) contain characters that are not permitted or have a special function in the URL syntax, they must be masked by other means."

### Consequence

- MG 4.3.1 says that all requirements of MG 4.1 also apply to the Oi4Identifier, and it names the dnp-encoding as the means. The dnp-encoding keeps exactly the unreserved characters `A–Z a–z 0–9 - . _ ~`; every other character is either not permitted or reserved (special function in the URL syntax). So "mask the offending characters with the dnp-encoding" equals "dnp-encode the whole element" – interpretation (a) of SF-104: deterministic (one Oi4Identifier per nameplate, MG 4.3) and reversible. The "may" of MG 4.3.1/A3 names the means, not an option to leave such characters unmasked.
- SF-104 → `decided` in the register (`726f2a3`), not `resolved`: the text of MG 4.3.1 and MG A3 still says "may". Aligning it ("may" → "must") is guideline text and needs a PO order (G-3.4 a). The PO was asked in the session and was not available; the question is in `REVIEW.md`. No re-baseline until then.

### Implemented (our side)

- `oec/spec/requirements/il.yaml`: REQ-IL-033 MAY → MUST, title "Oi4Identifier elements are dnp-encoded", MG 4.1 quote, refs SF-104 → `draft`. REQ-IL-022 "may be masked" → "are masked" → `draft`. REQ-IL-032 notes only point to the new keyword of REQ-IL-033 (mechanical remap, stays `reviewed`). The quotes of MG 4.3.1/A3 with "may" stay, because they are the current guideline text.
- New vector **V-PAY-245** (`draft`): MAM of an asset with SerialNumber `ABC@home`, ProductInstanceUri and DataSetWriterName unmasked → REQ-RES-MAM-006. `schema/tests/rule-layer.yaml` lists it (R-3).
- Oracle (`spec/tools/internal/payload/content.go`, test) and D7 (`conformance/internal/rules/rules.go`): the R-3 heuristic of REQ-RES-MAM-006 accepts only the dnp-encoded element (before: plain or dnp-encoded). For values of unreserved characters both are identical, so no reviewed vector changed its result. ADR-0019 R-3 got a note (mechanical consequence of the PO decision).
- `oec-core`: `Oi4Identifier::build` always dnp-encodes; `dnp_encoded()` and `Violation::SlashInElement` (`slash-in-element`) removed; unit tests cover `/`, space and `@`. The P3 sketch follows. ADR-0026 §5.2 rewritten, history kept (G-3.4 b).
- `project/research/guideline-digest.md`: masking mandatory.
- Views, export and coverage regenerated; schema unchanged (`2.0.1-dev`), release freeze green.

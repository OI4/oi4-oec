### 4. SDK snippets live (`sdk/rust.md`, `c.md`, `go.md`)

In `/tmp/c103/sdk`: the "first application" snippets extracted from the pages – Rust in a new crate with the path dependency (`cargo build` 39 s), C compiled with `-Wall` and linked per the page (`liboec_ffi.a` rebuilt with `cargo build --release -p oec-ffi`), Go in a new module with the `replace` directive (`go run ./cmd/oec-buildlib`, `go build`).

- First try, all three on `/tmp/oec-root` (the copy the D7 run had used for `demo`): every application refused to start – `DataSetWriterId 10 for MAM "…" conflicts with the assigned ids (REQ-MSG-021)`. The SDK keeps the ids of its application in `etc/oi4/app/oec/app/writer-ids` and pins the own MAM to 10; another application on the same store is refused. Even a Level 1 application writes the store, so Rust then C on one fresh copy fails as well. **By design** (REQ-MSG-021/RES-PUBLIST-006: ids are never reused for another key), not an SDK defect.
- Second try, one fresh copy each: the three applications reconnected about 125 times each in 150 s – the container name `oec-dev-app` in `etc/hostname` is the serial number **and the MQTT ClientId** (REQ-MQTT-013), so the broker dropped each one when the next one connected. **By design.**
- Third try, one copy each with its own `etc/hostname` (`hello-rs`, `hello-c`, `hello-go`), `monitor` started first, the apps stopped with SIGINT after 150 s: per application one `MAM` and four `Health` (Birth, after 60 s and 120 s, Close), and the registry's `Get MAM`/`Get Profile` were answered; `monitor --replay --app …` per application **13 pass, 6 skip, 0 fail** (inconclusive by design: a Level 1 application publishes no Data and no PublicationList, T7-MON-09/13/14 skip).

The C example `logger.c` received the Health of every participant for 70 s. The Go consumer snippet of `go.md` (addressed to a weather station): `Get Data` one answer with the station's values; `Set` with the normal login times out.

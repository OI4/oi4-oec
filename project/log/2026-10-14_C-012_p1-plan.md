## Observations that shape the plan

1. **No normative keyword convention.** MG 1.2 defines admonitions (`RECOMMENDED`, `HIGHLY RECOMMENDED`, `ATTENTION`) but not the meaning of shall/must/should/may; neither MG nor RIG references RFC 2119/8174 or the ISO/IEC Directives. Both "shall" (MG 107×, RIG 25×) and "must" (MG 136×, RIG 27×) are used. 12 `RECOMMENDED` boxes contain "the operator must prevent this via ACL", two `HIGHLY RECOMMENDED` boxes contain hard rules (MG 4.1 "different Identification Links", MG 4.2 "must not be used"). → **SF-032**.
2. **Immature chapters.** `ATTENTION – not maturely specified` boxes mark MG 10.3.1–10.3.5 (specific services Read, Write, Subscribe, Unsubscribe, GenericMethod) and MG 6.1.3/6.2.3 (process descriptions). It is open whether specific services count for any compliance level. → **SF-033**.
3. **External document.** RIG 5.1, 5.2 and the RIG 5 index refer to an external document "*Requirements for Interoperability*" that is not part of the guideline repo. → **SF-034**.
4. **Compliance levels are per requirement, not per area.** MG 1.3 / 8.2.1 and RIG 1.2 grade functions as Mandatory / Recommended / – per level (e.g. `Profile`: – / R / M; full MQTT client behavior: R / R / M). A single "level" field is not enough – the catalog needs an obligation per level.
5. **Appendix B is not machine-ready.** 113 `json` blocks in B1/B2, **62 of them do not parse** (25 with `//` comments, 27 with `<…>` placeholders, 10 other, e.g. ellipses/trailing commas). B1 pairs a topic line with a payload; B2 contains metadata payloads without topic.
6. **Roadmap area list is incomplete** for MG + RIG: compliance (MG 1.3/8.2, RIG 1.2), Locale, specific services, Registry (A1), container environment, SBOM/licenses, platform (RIG 5.1) and app-platform requirements (RIG 5.2) need their own areas.

## P1 plan (proposal)

### 1. Requirements catalog – format and location

**Location:** new folder **`oec/spec/`** = the machine-readable spec baseline, shared as a *contract* (like the D1 schemas) by schema tests, SDK, micro SDK, D7 and D8. Nothing in it is derived from SDK code (ADR-0006 stays intact). Proposed layout:

```
oec/spec/
  README.md                    what is here, how to cite REQ ids
  requirements/
    catalog.schema.json        JSON Schema 2020-12 for the catalog files
    areas.yaml                 area registry (code, title, guideline sections)
    <area>.yaml                one file per area, e.g. top.yaml, res-health.yaml
  topic/
    topic.abnf                 formal topic grammar (RFC 5234 + RFC 7405)
    topic-patterns.json        derived regexes (generic + per Method × Resource)
  matrix/
    method-resource.yaml       Method × Resource matrix
  vectors/
    topics/{valid,invalid}/    topic test vectors
    golden/                    curated Appendix B examples (topic + payload)
  tools/                       catalog lint, Markdown rendering, coverage, extraction (Go, cross-platform)
```

**Format:** YAML (comments, multi-line text, readable diffs), validated in CI against `catalog.schema.json`. A generated Markdown view per area is the review artifact for the PO. Alternative considered: JSON (no YAML dependency, worse to author/review).

**Entry fields** (draft; finalized with the catalog schema in the first execution cycle):

| Field | Content |
|-------|---------|
| `id` | `REQ-<AREA>-NNN`, e.g. `REQ-TOP-007`, `REQ-RES-HEALTH-003`; regex `^REQ-[A-Z]+(-[A-Z]+)?-[0-9]{3}$`; never reused or renumbered |
| `title` | short name |
| `statement` | normative statement in our words (one testable requirement per entry, atomic) |
| `keyword` | `MUST` / `MUST NOT` / `SHOULD` / `SHOULD NOT` / `MAY` as stated in the guideline (mapping per SF-032) |
| `domain` | `messaging` / `service-container` / `platform` (platform = RIG 5.1 + Registry, not graded by level) |
| `levels` | obligation per level, e.g. `{L1: none, L2: SHOULD, L3: MUST}`; derived from `keyword` + MG 1.3/8.2/RIG 1.2; `n/a` for `platform` |
| `applies_to` | subject/role: `publisher`, `subscriber`, `requester`, `responder`, `application`, `container-image`, `platform`, `registry`, … |
| `condition` | optional, e.g. "if `Set`/`Del` supported", "if `Data` is offered" |
| `refs` | guideline references: `MG 8.1.7`, `RIG 4.1.4`, `GL-ADR-013`, `SF-005` (+ optional short quote) |
| `verification` | one or more of `schema` (D1), `d7` (with mode `validate`/`monitor`/`test`), `d8`, `manual` |
| `maturity` | `stable` / `immature` (from guideline `ATTENTION` boxes, SF-033) |
| `status` | `draft` → `reviewed` (PO) → `deprecated` (with replacement id) |
| `notes` | optional |

Every file records the guideline revision it was written against (`baseline: 7bead4c`).

### 3. Topic grammar (ABNF + regex)

- **ABNF** (RFC 5234, case-sensitive literals per RFC 7405, e.g. `%s"Oi4v2"`) as the normative formal definition in `oec/spec/topic/topic.abnf`:
  - generic productions: namespace, ServiceType, AppId/Source (`b64url-level`), Method, Resource/service name, filter level (`topic-encoded-string`);
  - one production per Method × Resource combination with required/optional/forbidden `Source`/`Filter` levels and resource-specific filters (`<Tag>`, `<Context.Name>`, `<ResourceType>[/<Tag>]`, `<EventCategory>/<EventLevel>` with the closed level sets for Syslog, Status (`Good|Uncertain|Bad`) and Generic).
- **Percent-encoding in filter levels** (MG 8.1.7): `topic-encoded-string = 1*( unencoded-char / "%2B" / "%23" / "%2F" / "%25" )` where `unencoded-char` is any UTF-8 character except `+ # / %` (and U+0000, MQTT). Open points to check in C-014 and record as SF if needed: lowercase hex (`%2b`), empty levels, other `%XX` sequences.
- **base64url levels:** exactly one valid encoding per IL (MG 4.2) is expressible as regex: alphabet `[A-Za-z0-9_-]`, length ≤ 340, length mod 4 ≠ 1, and **canonical trailing bits** (2-char tail ends in `[AQgw]`, 3-char tail ends in `[AEIMQUYcgkosw048]`). Decoding + IL validity (ASCII subset, ≤ 255, lowercase authority, no `%`) is a rule check, not a regex.
- **Regex dialect:** the common subset of ECMA-262 (JSON Schema `pattern`), RE2 (Go, D7) and Rust `regex` – no look-around, no back-references, anchored. The regexes are **derived** from the ABNF and published in `topic-patterns.json` (generic + per combination) for P2 and D7.
- **Verification:** topic vectors (`valid`/`invalid`, each with the expected parse result and REQ ids) run against the regexes in at least two engines; the ABNF is checked with an ABNF tool (parse + random generation of valid topics that must match the regexes). All Appendix B topics are included as valid vectors.

### 4. Method × Resource matrix

- Source of truth: `oec/spec/matrix/method-resource.yaml`; rendered to a Markdown table for review.
- One row per combination of Method (`Pub`, `Get`, `Set`, `Del`, `Call`, `Reply`) × Resource / service (10 resources, `NewDataSetWriterId`, specific services). For each:
  - allowed yes/no;
  - topic: `Source` and `Filter` required / optional / forbidden, filter structure (→ ABNF production);
  - request payload: MessageType, `DataSetClassId`, content (e.g. `Get` = empty `Messages` or only helper DataSets with DSWID 1/3; `Set` = the new value);
  - response: topic (`Pub/<Resource>`, `Reply/<Service>`, `Pub/Event/<Source>/Status/<Level>` for Set/Del), correlation (`ReplyTo`, `RequestId`/`CorrelationData`);
  - obligation per level (MG 8.2.1) and condition;
  - REQ ids and guideline references (MG 8.1.4, 8.1.5, 8.2, 10.1.x, 10.2, 10.3).
- The ABNF per-combination productions and the matrix are kept consistent by a tool check (matrix ↔ ABNF ↔ vectors). Contradictions between MG 8.x and 10.x become SFs.
- Built in two steps: topic columns in C-014 (needed for the grammar), payload/response columns completed in C-017/C-018/C-019.

### 5. Golden examples from Appendix B

- An **extraction tool** (in `oec/spec/tools/`) reads Appendix B at the baseline revision and writes one vector per example to `oec/spec/vectors/golden/`: `{source: {doc, section, heading, index, rev}, topic, payload, expected, reqs, edits}`. Re-running it after a guideline change shows what changed (supports the guideline-evolution track).
- **Curation rules:**
  - Illustrative non-JSON (`//` comments, `{ //additional … }` placeholder elements, ellipses) is removed; each removal is recorded in `edits` (JSON Pointer + reason). No content is invented.
  - Examples with `<…>` placeholders (templates) are not vectors unless the placeholder can be replaced by a value fixed by the guideline (recorded in `edits`).
  - If an example contradicts a REQ: new SF; until the PO decides, the vector keeps the guideline content, is marked `expected: invalid` with the violated REQ id and the SF id. Once decided, the corrected vector gets an `edits` entry referencing the SF.
  - B2 metadata examples (no topic) become payload-only vectors.
- Golden vectors are the first **positive** vectors: P1 checks their topics against the grammar; P2 checks their payloads against the schemas. Negative vectors per REQ follow in P2.

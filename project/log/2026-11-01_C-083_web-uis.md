## Intent

Build increment 5 of P6: a small Web UI for each demo, using technique D-3 (a) and ADR-0028 §3. Each UI:

- is static HTML/CSS/JS embedded in the binary, with no build step, framework, npm or CDN;
- offers JSON snapshots under `/api/` and live updates by Server-Sent Events (`GET /api/events`, keep-alive every 15 s);
- uses `POST` only where something is edited;
- listens on loopback without authentication or TLS (A-305), hardened like the API of C-082 (A-357).

The three UIs:

- **logger (C):** the last records with filters, live, plus charts. This needs an HTTP server in C; choosing it is part of this increment.
- **weather service (Go, `net/http`):** the stations with their values, a short SVG history, Health and the provider; the MET Norway credit while `met-no` is active (A-351).
- **config service (Rust, `std::net`):** the applications and one form per `Config`, built from its definition. Only writable `Config`s are editable, masks stay masks, and the `Status` result of every `Set` is shown (A-304).

The tests are HTTP/SSE tests with the Go client against the running demos; there is no browser in the gate (§6.4). The D7 pins stay unchanged: logger 46 (L2), weather 49 (L3), config 22 (L1).

### 2. The common contract (A-359, `internal/demotest/webui.go`)

All three servers follow one set of rules, which the same Go helpers check against each running demo:

| Helper | Checks |
|---|---|
| `UIAddr`, `WaitUI` | a free loopback port; waits until the UI answers |
| `CheckStatic` | `GET /`, `/app.css`, `/app.js` with their types and the common headers; no external resource in HTML, CSS or JS; `fetch` only below `/api/` |
| `CheckGuards` | `Host` other than `localhost` or an IP literal → 403, foreign `Origin` → 403, `Transfer-Encoding` → 501, `POST` without JSON → 415, body > 64 KiB → 413, head > 8 KiB → 431, unknown path → 404, unknown method → 405 with `Allow` |
| `CheckSlow` | a request that is not complete after 5 s → 408 (the weather service on `net/http`: the connection is closed) |
| `CheckLimits` | 8 event streams, the 9th → 503, a place frees when a client leaves; 16 connections, the 17th → 503 |
| `CheckKeepAlive` | the comment `: keep-alive` on an idle stream (`OEC_UI_KEEPALIVE_MS` short in tests) |
| `Events`, `SSE.Event` | an SSE reader with typed JSON events |

Every answer carries `Connection: close`, `Cache-Control: no-store`, `X-Content-Type-Options: nosniff`, `Content-Security-Policy: default-src 'self'; frame-ancestors 'none'` and `Referrer-Policy: no-referrer`.

`OEC_UI_LISTEN`:

- empty switches the UI off ("Web UI off" on stderr);
- an invalid address, a missing host (`:8781`) or a busy port ends the program with exit ≠ 0, before it connects to the bus;
- unset means `127.0.0.1:<port>`.

The D7 runs switch the UI off (`OEC_UI_LISTEN=`), so the D7 setup stays as before. `Process.Exit` (wait for an exit without a signal) was added to the harness.

### 3. Logger – the C server and the UI (commit `21c4a38`)

**Choice of the server (A-360):** an own minimal HTTP/1.1 server on POSIX sockets, `logger/src/http.{h,c}` (C17, pthreads, `poll`), with no library.

- The subset is small: one request per connection, `Content-Length` bodies only, no chunked input, no keep-alive, no TLS.
- A library (e.g. a small permissive embedded server) would bring a license review, a vendored copy and an update duty for a few hundred lines of code. The dependency policy prefers no new C dependency (ADR-0028 §7, as for the JSON reader).
- Structure:
  - one accept thread that polls for the stop;
  - one thread per connection from a fixed table of 16 slots; a 17th connection gets 503;
  - event streams count against a limit of 8.
- `lh_parse` checks the head in the order of the guards above. It is a pure function and unit-tested: request line, header syntax, repeated headers, `Content-Length`, Host and Origin rules, query decoding, listen addresses.
- Reading and writing have a deadline of 5 s (`poll`). A client that is too slow or has gone ends its stream.
- After an answer, the server shuts the socket down for writing and drains the input briefly before it closes. This avoids the RST of C-082 (`finish()`).

**UI routes (`logger/src/ui.{h,c}`), read only:**

| Request | Answer |
|---|---|
| `GET /api/status` | version, state, the settings in force, number of records, last sequence number, number of series |
| `GET /api/records?limit&after&resource&level&q` | the newest matching records (`limit` 1 … 10000, default 200); invalid parameters → 400 |
| `GET /api/series` | the numeric series of `Data`/`Health` |
| `GET /api/events` | `status` first and on a change of the settings or the state; `record` for every new record (batches of 64); `reset` when the stream fell behind the ring buffer |

The history (`history.{h,c}`) got sequence numbers, a wait for new records with a timeout, and a filtered query. The settings stay the OEC `Config`, changed on the bus (e.g. by the config service); the UI shows them read only and has no `POST`.

**Embedded files (A-361):**

- `internal/cembed` (Go, standard library) turns `logger/ui/` into `logger/src/ui_assets.c` (byte arrays, path, content type).
- The generated file is committed, so building the logger needs no Go.
- `TestUIAssets` fails the gate when the file is not current, like the `oec.h` diff.

**Page:**

- state, settings, a records table with filters (resource, level, text, maximum, pause) and live records;
- per series an SVG polyline (up to 240 points).

**Tests:**

- unit tests in `test/unit.c`: HTTP parser, query, listen, history query/wait/sequence, JSON of the routes; ASan + UBSan, C17 with `-Wall -Wextra -Wpedantic -Werror`;
- `logger/webui_test.go`:
  - `TestWebUI`: files, status with the settings, records live by SSE and by snapshot with every filter, series, guards, time limit, limits, keep-alive;
  - `TestWebUIListen`;
  - `TestUIAssets`.

### 4. Weather service – the UI on `net/http` (commit `89a3a3f`)

- `weather/ui.go`:
  - `http.Server` with `ReadHeaderTimeout`/`ReadTimeout` 5 s, `MaxHeaderBytes` 8 KiB and keep-alives off;
  - a listener that holds at most 16 connections (503 at once beyond);
  - one guard middleware for Host, Origin, TE, Content-Type and body size;
  - the files via `embed`.
- **Snapshot `GET /api/state`:** state, version, provider, poll interval, thresholds, Health of the application and, per station:
  - location, SerialNumber, Health and score;

  The poll goroutine builds it under the lock of the service and never waits for the HTTP side.
- **MET Norway credit (A-351, A-362):**

  - The text and the URLs come from the Go code, which also has the README text, and not from the JS. `TestMetNoProvider` checks that the credit appears with `met-no` and disappears after the switch back to `simulation`.
- **`GET /api/events`:** `state` first, after every poll round or applied `Config`, and on a change of the connection state.
- **Page:** a card per station with values, warnings, Health, an error, and an SVG line of temperature and wind speed.
- **Tests:** `weather/webui_test.go` (`TestWebUI`, `TestWebUIListen`); the rig of `weather_test.go` runs every service with a UI on a free port.

### 5. Config service – SSE and the UI on `std::net` (commit `484700a`)

**Server additions (A-363):**

- `src/events.rs`, a hub of at most 8 subscribers with a queue of 64 messages each:
  - `subscribe` gives `None` when the hub is full (→ 503);
  - `send` never blocks: a subscriber with a full queue or a closed connection is dropped;
  - a subscription leaves the hub on `Drop`.
- `http.rs`:
  - the common headers;
  - `Request.query` (any query → 400, no route takes one);
  - a streaming response: head without `Content-Length`, `data:` lines, keep-alive comments, a non-blocking read to notice a client that left, and the end on a write error.
- `api.rs`:
  - the files via `include_str!`;
  - `GET /api/events` with `apps` first;
  - every result of `POST /api/set` (also 504) as the event `set`;
  - 405 with `Allow` for the files and the stream.
- `main.rs`:
  - `OEC_UI_KEEPALIVE_MS` and the listen address are checked and bound before `App::builder`;
  - a broadcaster thread compares the apps snapshot every 250 ms while streams exist and sends `apps` when it changed;
  - "Web UI on http://…/" or "Web UI off" on stderr.
- A-357 changes accordingly: `GET /` is now the page, `/app.css`, `/app.js` and `/api/events` are new, and a query is refused.

**Page (`config/ui/`, A-364):**

- **Applications list:** state and Health, live; the first application is chosen automatically. *Discover again* (`POST /api/refresh {}`) and *Read again* (one application).
- **Details:** MAM (Manufacturer, Model, ProductCode, SoftwareRevision, …), Profile, SubscriptionList, errors of the discovery.
- **One form per `Config`, from its definition:**
  - `Validation.Values` → select; Boolean → select `true`/`false`;
  - Number → number field with `Min`/`Max`;
  - `Length` → maximum length;
  - `Pattern`, `Unit`, `DefaultValue`, `Mandatory` and the description as hints only: the target validates (A-356).
- **Non-writable `Config`s** (SF-107): disabled fields and the note "read only".
- **`Sensitive` objects:**
  - a password field with the placeholder `******** (unchanged)`; empty means "unchanged" and is not sent (the service sends the mask back, GL-ADR-021);
  - a Boolean `Sensitive` object is a select with an empty "unchanged" option;
  - a value the user typed is never shown again.
- **Send:** only changed values are sent; the service adds the `Mandatory` ones. The result (`Good (0x00000000)`, `BadOutOfRange (0x803C0000)`, 504, …) stays under the form.
- **Live updates:** a form keeps its fields while it is unchanged or edited. When the application publishes a new `Config` while the user edits, the form shows "The application changed this Config" with a reload button instead of overwriting the input.
- **Set results:** the table of `GET /api/sets` plus every `set` event, at most 100 rows.

**Tests:**

- unit tests 20 → 26, among them `http::tests::event_streams` and the two tests of the hub;
- `config/webui_test.go`:
  - `TestWebUI`:
    - files and the `apps` event;
    - the logger's `Config` writable;
    - a Good `Set` with its `set` event and an `apps` event with the new value;
    - a refused `Set` (`minEventLevel` = `Loud`) with a non-Good `set` event;
    - an unknown object → 400 without an event;
    - a query → 400, `POST /api/events` → 405;
    - guards, time limit, limits, keep-alive.
  - `TestWebUIListen`: off, invalid and busy addresses, invalid keep-alive values.
  - `startService` takes extra environment; the test lists the logger in `apps`, because its Birth message came before the service started and is not retained.

## Risks and open technical points

- **No authentication:** anyone on the host can use the UI. That is acceptable on loopback for a demo (A-305). The C-084 containers listen on `0.0.0.0` inside the container; compose must publish the ports on `127.0.0.1` only (ADR-0028 §3).
- **Thread per connection (logger):** bounded by 16, so at most 17 threads.
- **Polling for changes (config):** the broadcaster compares the snapshot every 250 ms while a stream is open. That is cheap for a demo, but not a pattern for many applications.
- **Masks not end to end:** no demo has a `Sensitive` object (A-364). A later demo with a secret could cover it.

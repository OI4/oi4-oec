### 2. D2 Rust API sketch (`2b6b390`)

`oec/sdk/rust/sketch/` is a crate `oec-api-sketch` with library name `oec`, so the examples read like the real SDK. It has no dependencies (builds offline) and every body is `unimplemented!()`.

- Modules: `app`, `identity`, `asset`, `data`, `config`, `event`, `consumer`, `status`, `store`. The doc comments of the public items cite the REQ ids they implement; the module map, flows and defaults are in `README.md`.
- DX sketches:
  - `hello.rs` (16 lines);
  - `device_source.rs` (L3 OTConnector, represented device, Oi4Pv DataSet, Precision, writable PublicationList entry, `on_set` with range check, updates from a plain thread);
  - `config.rs` (Number with unit/min/max/mandatory, sensitive String, own rule in `on_set`);
  - `consumer.rs` (subscribe, presence, blocking and async `Get`).
- Test `tests/sketch.rs`:
  - hello world ≤ 20 lines;
  - every `REQ-…` id cited in a `.rs/.h/.c/.md` file under `oec/sdk/` exists in `oec/spec/requirements` and is not deprecated (more than 100 citations required).

Main design rules (ADR-0020):
- the level is chosen, the protocol is automatic (mandatory and recommended behavior of the level on; `build()` rejects configurations that cannot keep it);
- state, not messages (the PublicationList entry decides when to publish; the last state answers `Get`, pagination from a snapshot);
- blocking by default, `run_async` for tokio users; consumer requests async with `_blocking` twins;
- handlers decide, the SDK answers (fixed `Set` pipeline with automatic Status event);
- strict sender (embedded schemas, ADR-0019 §7), tolerant receiver.

### 3. C ABI sketch (`21205db`)

`oec/sdk/rust/sketch/c/include/oec.h` is the hand-written contract that the cbindgen header must keep in P4 (ADR-0021):
- opaque handles with clear ownership; the builder is consumed by `build` in every case;
- borrowed input strings and owned output strings with `oec_string_free`;
- JSON text for definitions and values;
- `oec_status` plus a thread-local `oec_last_error`; panics never cross the ABI;
- callbacks on an SDK thread, one at a time per app;
- `OEC_ABI_VERSION`.

Examples: `hello.c`, and `logger.c` (the shape of the D4 logger in C, Q-024).

### 4. D9 API sketch (`d481fdc`)

`oec/sdk/micro/sketch/include/oecm.h` with `examples/hello_device.c` (ADR-0022):
- prefix `oecm_` (Q-025);
- caller-allocated device state and transmit buffer, no heap;
- borrowed `const` configuration with the MAM;
- PAL struct with `ctx` (MQTT with TLS, clocks, persistence);
- single-threaded `oecm_poll` model;
- a new Will per connect;
- a wall clock is required.

The README maps the PAL to ESP-IDF. **Finding for the port:** esp-mqtt's automatic reconnect reuses the configured Last Will, but REQ-LIFE-016 needs a new Will (MessageId with creation time) on every connect. So the port disables the auto-reconnect and the core reconnects itself.

### 8. Spec findings (guideline register `f80eba7`, register-only)

- **SF-101** (MG 8.3.8): every publishing `Mode` "additionally" allows `Get`, so `ON_REQUEST` in the combined values adds nothing, and it stays open whether `FILTER_4` without `ON_REQUEST` answers `Get`.
  - Proposed: every Mode except `OFF_0` allows `Get`, with proposed MG text.
  - The SDK defaults contain `ON_REQUEST` for every resource with `Get`, so they hold under both readings.
- **SF-102** (MG 7.2/1.3): no `ServiceType` for a directly connected smart device.
  - Proposed: `OTConnector`, with proposed MG text; the alternative is a new value, which needs a new guideline version and a schema change.
  - The D9 sketch uses `OTConnector`.

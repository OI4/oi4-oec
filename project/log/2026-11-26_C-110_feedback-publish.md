- Date: 2026-11-26
- Phase: P9 – Hardening & release, increment 7 (ADR-0032 §10; C-109 addendum 1, A-613)
- Baseline: guideline `52d8470` (branch `feature/spec-findings`, head `ae64fc3` before the cycle: the Community page of C-109, no guideline chapter changed); SF-001 … 117 resolved, next SF-118

## Goal

Increment 7 as handed over: (1) the **feedback package for the work group** – every spec finding SF-001 … 117 with finding, decision and the text that implements it, and the guideline diff from the state before our changes to `52d8470`, readable for people who do not know the project; format, structure, place and generation with reasons (A-x); a completeness check (every finding exactly once, every change of the guideline attributed); how and to whom it goes is the PO's (D-x, Q-011). (2) The **publishing step** of C-109 D-3 (a) (A-613): a job behind the release build that publishes the GitHub Release on `OI4/oec`, the images on GHCR and the Go module tags – tests first, the logic in a script, inert until the PO's go; what it needs from the PO as D-x.

## Plan

1. **Range of the package:** base `5f070bb` (the guideline baseline of C-006: the Docusaurus guideline with GL-ADR-001 … 011 as the PO brought it into the project; the first finding commit `931836a` follows it) to `52d8470`; the documents MG (`docs/guideline`), RIG (`docs/infrastructure-guideline`), GL-ADRs (`rfcs_adrs`), the informative Process Description (`docs/process-description`) and the figures (`static/img/guideline`). The site code (`src/`), the Community pages and the old Confluence export are not guideline text.
2. **Attribution instead of hunk matching:** the cumulative diff is the sum of the commits in the range; a hand-maintained table `findings/feedback/attribution.tsv` in the guideline repository assigns every commit that changes the documents to findings (`SF-xxx`), GL-ADRs or one class for the rest (editorial, figures, …) with a neutral note – the commit subjects are informal. Merge commits must not carry changes of their own (checked).
3. **Generator `spectool feedback`** (oec/spec/tools, standard library, git as the existing `inventory` uses it; tests first): reads the register, the attribution and the history; writes `findings/feedback/README.md` (what, scope, how to read, numbers, index), `findings.md` (each finding once: area, finding, decision, status, the commits with their files and a word diff of the Markdown) and `other-changes.md` (GL-ADR and editorial commits). `-check` (gate step 1): the attribution is complete and consistent and the committed package equals the rendering.
4. **Publishing step (new ADR-0034):** `oec/ci/publish.sh <release dir>` – verifies `SHA256SUMS`; builds the release repository commit (the `oec/` tree of the source archive; the `replace` directives between the Go modules replaced by the release version, `go.sum` completed by the go command from a local copy of the release repository, tags `v<v>` and `<module>/v<v>`); the images from the OCI archives to `ghcr.io/oi4/…` (skopeo); the GitHub Release with the files of `oec-release` (gh). Dry run by default (prepares and verifies everything, publishes nothing); publishes only on a release tag in a job `publish` with the GitHub environment `release` (the PO approves each run) and its secret. Model extension of `oec/ci/gha` (job `if`, `environment`, job permissions; tests first), `release.yml` regenerated.
5. **Local verification:** the package check in the gate; `publish.sh` dry run on the Mac against the C-109 release build: `go install …/oec-check@v<v>` from the local release repository offline; the image push into a local registry from an Ubuntu container (skopeo); shellcheck, actionlint, `linux.sh`, the gate. Hosted and publishing-only items open for C-111/the first release.
6. **Docs:** ADR-0034, amendments (ADR-0032, ADR-0033, ADR-0018 for spectool), READMEs, Community pages if affected, ROADMAP, STATUS, REVIEW/REVIEW_DE (A-614 ff., D-1 ff.).

## Result

Increment 7 is built and verified locally. **The feedback package** `findings/feedback/` in the guideline repository (136 files, 1.9 MB Markdown, generated by `spectool feedback`, checked in gate step 1): every finding SF-001 … 117 on its own page with the register entry and the commits that implement it (files and word diff), one page per guideline ADR with commits (13), the other 73 commits in three classes `normative.md` (7 – please review like a finding), `wording.md` (20), `editorial.md` (46), and `files.md`; every one of the 211 commits that change the guideline documents between `5f070bb` and `52d8470` is attributed by hand in `attribution.tsv` (A-614 … A-618, ADR-0018 amendment C-110). **The publishing step** of C-109 D-3 (a): `oec/ci/publish.sh` and the job `publish` of `release.yml` behind the GitHub environment `release` (ADR-0034, A-619 … A-623); every release run makes a dry run that prepares the commit and the twelve Go module tags of `OI4/oec`, checks them with `go install …/oec-check@v<v>` and checks the images; only an approved tag build publishes. How the package goes to the work group (**D-1**) and the prerequisites and the go for the first release (**D-2**) are the PO's.

The plan named two files `findings.md`/`other-changes.md`; the package became one page per finding instead – one file for the other changes would be about 450 KB (the three class pages are 40 + 132 + 279 KB), beyond what GitHub renders, and a page per finding can be linked from a review comment.

### 2. The publishing step (ADR-0034, A-619 … A-623)

- **Model `oec/ci/gha`** (`a060475`, tests first, `TestRenderEnvironment` with ten rejected cases): job `if` and `environment`; the environment secret `OEC_RELEASE_TOKEN` only in the `env` of a run step of a job in the environment `release`; no environment with a `pull_request` trigger; `if:` conditions checked for untrusted contexts (ADR-0032 amendment C-110).
- **`release.yml`** (`98f92b5`, `TestPublish` first, `TestRelease` adjusted): the job `release` runs `publish.sh dist/release` (dry run) before the upload; the new job `publish` (needs `release`, `if: github.ref_type == 'tag'`, environment `release`, `ubuntu-24.04`, 60 min) downloads `oec-release` and runs `publish.sh dist/release --publish` with the token and `vars.OEC_RELEASE_USER` in its `env`; `contents: read` unchanged – unlike the plan ("`contents: write`, `packages: write` in this job"), the `GITHUB_TOKEN` of `OI4/oi4-oec` cannot write to the other repository `OI4/oec`, so the write right comes only from the environment secret (ADR-0034 Alternatives); `cigen: 7 workflows current`.
- **`oec/ci/publish.sh`** (`98f92b5`): checks `SHA256SUMS` (exactly the files of the directory), version, commit and source; prepares the release repository from the source archive (sibling `replace` → `require …@v<v>`, `go.sum` by `go mod tidy` against the prepared repository via `insteadOf`, empty module cache, `GOPRIVATE`; tags `v<v>` and `<dir>/v<v>` for the twelve modules; the commit with the source commit's time and a fixed author); checks it with an empty cache (`go list -mod=readonly -deps -test`, `go mod verify` per module, `go install …/oec-check@v<v> …/oec-infra@v<v>` with the module's toolchain); checks the image indexes (linux/amd64 + linux/arm64) and their digests; writes the release body. `--publish` only on the tag build `oec-v<v>` of a release version: atomic push, `skopeo copy --all --preserve-digests` to `ghcr.io/oi4/oec-<image>:<v>`, `gh release create --verify-tag` – in this order; reruns keep tags with the same tree and fail on another tree or an existing release; the token only in an HTTP header from the environment, an authfile (mode 600) and `GH_TOKEN`.
- `release.sh`: the "workflow artifact only" sentence of the notes stays for snapshots; a release says how to check the files (`TestRelease` still forbids push/login/publish/upload in the script).
- **D7/D8 report the module version after `go install …@v<v>`** (`0b8ff91`, A-623; test first `TestToolVersion`, 17 cases): the first dry run showed `oec-check dev` from the release repository. `report.ToolVersion` takes the stamped version (`-X main.version`, unchanged), else the module version of the build info, else `dev`; pseudo-versions and `+dirty`/`+incompatible` count as none. `var version = "dev"` stays a constant initialiser so that `-X` keeps working (checked: `-X main.version=9.9.9` → `oec-check 9.9.9`). Additive; report format unchanged. Pages: `oec/conformance/README.md`, Community `compliance/index.md` (guideline `09f0914`); `oec/CHANGELOG.md` names the channels.

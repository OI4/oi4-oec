## Intent

Build increment 4 of P6: the core of the config service D10 in Rust on the SDK crate `oec` (ADR-0028 §7, A-304). It is an own Cargo package `oec/demos/config` with ServiceType `Utility` at Messaging Level 1. The service:

- finds the applications on the bus (`Pub/MAM`, and `Get MAM` at the start);
- reads their `Config` and `SubscriptionList`, and knows which `Config` is writable (SF-107);
- sends `Set Config` and evaluates the `Status` event; masked values go back as the mask (REQ-RES-CONFIG-025);
- is configured by a file and the environment, with the broker from `broker.json`;
- is operated without a Web UI through a small internal API, which the tests use now and the Web UI uses in C-083.

The gate runs the Rust checks of the package and D7 `level1` against the binary. An integration test lets the service find and edit the logger and the weather service.

Nothing was open for the PO and no answer arrived. No split: the cycle takes increment 4 only.

### 3. Package `oec/demos/config` (A-354 … A-357)

**Package:** an own Cargo package `oec-config` 0.1.0, edition 2024, MIT, `publish = false`, with an empty `[workspace]` so it stays outside the SDK workspace.

- **Dependencies:** `oec` by path, plus `serde_json` and `log`. Both are already in the SDK lock and inside ADR-0023, so there is **no new crate**.
- **`Cargo.lock`:** its own, generated offline from the SDK lock (a subset of its versions).
- **Lints:** as in the SDK (clippy pedantic, `unsafe_code` forbidden).
- **cargo-deny:** runs with the `deny.toml` of the SDK and passes (licenses, advisories, bans, sources).

**Identity:**

- `Utility`, L1;
- Product `oi4.org` / "OEC Config" / `OEC-CONFIG`, manufacturer "Open Industry 4.0 Alliance";
- AppId `oi4.org/OEC,20Config/OEC-CONFIG/<hostname>`.

**Modules:**

| Module | Content |
|---|---|
| `settings.rs` | The optional file `<OEC_ROOT>/etc/oi4/app/config-service.json` or `OEC_CONFIG_FILE` (explicit and missing → error); `OEC_UI_LISTEN` overrides `listen`. Strict: unknown keys and invalid values stop the start. Keys `listen` (default `127.0.0.1:8783`), `requestTimeoutSeconds` 1 … 60 (5), `apps` as `<ServiceType>/<AppId>`, `setHistory` 1 … 1000 (50) |
| `topic.rs` | IL levels and Filter encoding of the topic, the `Set Config` topic, MQTT filter matching for the entries of a SubscriptionList |
| `directory.rs` | The model without I/O: applications (online/offline, MAM, Profile, Configs by Source and context, SubscriptionList, errors), the writability rule (SF-107), the checks and the payload of a `Set`, the bounded history of `Set` results |
| `service.rs` | The bus side on `oec::Consumer`: presence, the live subscription to `Pub/Config`, a worker thread for discovery, `refresh`, `set` |
| `http.rs`, `api.rs` | The HTTP/1.1 server on `std::net` and the routes of the API |
| `main.rs` | The logger on stderr (`OEC_CONFIG_LOG`) through `oec::event::install_bridge`, the `App`, `on_connection`, the worker and HTTP threads, `App::run` |

**Discovery (A-355):**

- **Triggers:**
  - every Birth (the SDK's `on_presence`, REQ-LIFE-003/013) of an application that is new or was offline;
  - at every connect, `Get MAM` to the applications of `apps`, then a new discovery of every online application (a reconnect rediscovers everything);
  - `POST /api/refresh`.
- **Per application:** `Get Profile`, then `Get Config` and `Get SubscriptionList` when the Profile lists them. The answers are parsed from `payload_json`.
- **Writable:** a `Config` is writable if the SubscriptionList lists its `Set` topic, also by a wildcard (SF-107, REQ-RES-SUBLIST-016).
- **Updates:** `Pub/Config` of any application updates the cache. A Close message or a Will marks the application offline (REQ-LIFE-011/012).
- **Self:** the service never lists itself.
- **Threads:** no tokio in the service. The blocking calls of the SDK cannot run on tokio threads, so one worker thread does every discovery job one after the other. A set of pending jobs drops duplicates. The HTTP threads call the blocking calls themselves.

**`Set Config` (A-356):**

- **Structural checks only:**
  - unknown group or object → 400;
  - a value that is not a string → 400 (REQ-RES-CONFIG-007);
  - unknown application or `Config` → 404;
  - offline or not writable → 409;
  - not connected → 503.
- **The target decides on the values** (Type, Validation, rules across objects: REQ-RES-CONFIG-023). The service does not duplicate them, so one generic tool works for every application, also for rules it cannot see (e.g. A-348 of the weather service).
- **Payload:**
  - every `Mandatory` object of the group that is missing is added with its current value (REQ-RES-CONFIG-011);
  - a `Sensitive` value is published as the mask `********` and is sent back unchanged as the mask, which keeps the secret (REQ-RES-CONFIG-025, GL-ADR-021);
  - a new secret is sent as given and never shown; the history keeps the mask;
  - the `DataSetWriterId` of the `Config` is used.
- **Outcome:**
  - the `Status` event of the target comes back with HTTP 200, also for Bad (`good: false`);
  - no answer within the timeout → 504; not connected → 503; any other error → 500;
  - after a Good status the service reads the `Config` again;
  - every result goes into the history (newest first) and into the log.

**HTTP API (A-357):**

- **Endpoints:**
  - `GET /api/apps`;
  - `POST /api/refresh` (all, or one application; an unknown one gets `Get MAM` first, 404 without an answer);
  - `POST /api/set`;
  - `GET /api/sets`;
  - `GET /` (a text note until C-083).
- **Format:** JSON, HTTP/1.1, one request per connection.
- **Hardening:**
  - `Host` must be `localhost` or an IP address and `Origin` must be its own, else 403 (DNS rebinding, cross-site POST);
  - POST requires `application/json` (415);
  - `Transfer-Encoding` → 501; repeated headers → 400;
  - limits: body 64 KiB (413), head 8 KiB (431), 5 s per request (408), 16 connections (503);
  - response headers `Cache-Control: no-store` and `X-Content-Type-Options: nosniff`;
  - after a response the server closes its write side and drains the socket for up to 100 ms, so a client never sees a reset instead of an early error answer.
- **No authentication and no TLS:** a demo (A-305). The default is loopback, port 8783 (ADR-0028 §3).
- **SSE** follows with the Web UI in C-083.

## Agent decisions (G-3.4 b, for information: REVIEW A-353 … A-358)

- **A-353 SDK getter:** `Received::writer_group_name()` (ADR-0020 amendment C-082), additive, test first. C ABI and Go SDK unchanged.
- **A-354 No own OEC `Config`:**
  - The settings of the service (HTTP address, timeout, known applications, history) concern only the service and are not on the bus.
  - An own `Config` would need Level 2 (`Get`/`Set` answers), against the declared L1 (A-301), and a config tool that edits itself over the bus adds nothing.
  - Settings come from a JSON file and the environment, the broker from `broker.json` through the SDK.
- **A-355 Discovery and threads:**
  - Discovery runs on Birth/presence, on `Get MAM` at every connect to the configured `apps`, again for every application after a reconnect, through the live `Pub/Config` subscription, and on `refresh`.
  - One worker thread for discovery and no tokio of its own, because the blocking SDK calls must not run on tokio threads.
- **A-356 `Set` semantics:**
  - Only structural checks; the target validates (REQ-RES-CONFIG-023).
  - Missing `Mandatory` objects are added with their current value (REQ-RES-CONFIG-011); the mask is kept (REQ-RES-CONFIG-025).
  - Every result is recorded; after Good the `Config` is read again.
  - HTTP 200 for every `Status` event, 504/503/500 when there is none.
- **A-357 HTTP API:**
  - `std::net` with no new crate; the endpoints above, JSON, one request per connection.
  - The hardening above; no authentication or TLS (A-305); loopback port 8783 by default.
  - The API is internal: the tests and the C-083 Web UI use it, and it may change with C-083. SSE follows in C-083.
- **A-358 Tests and gate:**
  - 20 unit tests and four Go integration tests.
  - D7 L1 with 22 pins in the gate; `oec/demos/check.sh` gets the Rust block.
  - `reqs_test.go` scans `.rs`/`.toml` files.

## Risks and open technical points

- **No local validation:** a `Set` with a wrong value is only refused by the target. The Web UI (C-083) may show the `Validation` of the definition as a hint, but the target stays the judge.
- **One request per connection:** enough for a demo UI. SSE in C-083 needs a long-lived connection outside the 16-connection limit, or a separate limit.
- **Visible contact:** the contact of the weather service (`userAgentContact`) is personal data, not a secret, and is shown as published (C-081 note).
- **Discovery traffic:** each new application costs three requests. With many applications the worker serializes them; the timeout bounds a silent one.

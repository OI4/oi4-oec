## Goal

Increment 4 as handed over: multi-arch images (linux/amd64, linux/arm64) of the three demos, the registry and D7/D8, built in a generated workflow and checked with D8 `image` and `run` – no push to a registry (Q-011); the newcomer runs: "Getting started" on a fresh Ubuntu (compose profiles `demos`/`registry` of `oec/dev`), the limits on Windows, the live run `oec/conformance/live.sh` (incl. `TestRunDev`, the "`live-infra.sh` run" of ADR-0025 amendment C-074 item 7) on a Linux runner, Podman on Linux. ## Plan

1. **Tool image `oi4/oec-conformance`** (ADR-0025 §10 named "a multi-arch image"; A-237 deferred it to P9): `oec/conformance/Dockerfile` with `oec-check` and `oec-infra` (static, `CGO_ENABLED=0`), SBOM and license texts in `/opt/oi4/licenses` by `oec-sbom`; the Go modules of D7/D8 are not of this workspace, so `oec-sbom` gets a license map of the third-party Go modules (additive, test first). 2. **`images.yml`** (ADR-0032 §6 named it), generated by `oec/ci/pipelines` (test first): on `ubuntu-24.04` and `ubuntu-24.04-arm`, `oec/ci/images.sh` builds the five images for both platforms (D8 `image` on the OCI archives, D8 `run` on the native image), then `oec/ci/getting-started.sh` walks the "See OEC at work" path of the Community page with these images (compose, Web UIs, a `Set` through the config service, the new station in the registry), then `live.sh` with `OEC_LIVE_REGISTRY=1`. A Podman job on `ubuntu-24.04` for what Podman can do. No image archive as an artifact (publication is the PO's, Q-011); D8 reports as artifacts.
3. **Local verification:** `lint.sh`, the scripts on the Mac (own builder, own tags – a compose stack of another session runs on this Docker), the newcomer path and `live.sh` in a fresh Ubuntu container with its own Docker engine, Podman in an Ubuntu container, `linux.sh`, the gate.
4. **Docs:** `oec/ci/README.md`, `oec/dev/README.md`, `oec/conformance/README.md`, Community pages (Getting started: Linux, Windows, Podman; `oec-check`/`oec-infra`: the image), ADR-0032/0025 amendments C-107, ROADMAP, STATUS, REVIEW (A-584 ff.).

## Result

Increment 4 is built and verified locally: the generated workflow `images.yml` builds five multi-arch images (linux/amd64 and linux/arm64) – `oi4/oec-logger`, `oi4/oec-weather`, `oi4/oec-config`, `oi4/oec-registry` and the new tool image `oi4/oec-conformance` – judges each with D8 `image --level 3` and each application with D8 `run --level 3`, walks Getting started with the images, runs the live D7/D8 tests (`TestRunDev` included) and, on amd64, all of this under rootless Podman. No image leaves the runner (Q-011). In a fresh Ubuntu 24.04 (arm64) with its own Docker engine every step passes, under Docker and under Podman 4.9.3. Four issues were found on the way, all in the new scripts or a trial setup (none in a deliverable). Windows is documented, not in CI. Nothing to decide; the hosted runs follow in C-111 (C-105 D-2 (b)).

### 3. Podman on Linux (A-591)

Rootless Podman 4.9.3 of Ubuntu 24.04 (CNI backend, slirp4netns, cgroups v2) in an Ubuntu container; Docker Compose 2.40.3 as the compose provider. Found step by step, fixed, and now every step works (`OEC_PODMAN_LIMITS` empty):

| Problem | Cause | Measure |
|---------|-------|---------|
| `podman compose up` refused | Docker Compose rejects `healthcheck.start_interval` against Podman 4.x (API < 1.44) | additive override `oec/dev/compose.podman.yaml` (`start_interval: !reset null`, `interval: 5s`); test `TestComposePodman` first; `podman.sh` adds it by a wrapper |
| `--wait` hung (1307 s) | Podman runs health checks by systemd timers; none without user systemd | ticker in `podman.sh`: `podman healthcheck run` on containers with `health=starting` every 2 s |
| `mosquitto:8884` not resolvable | no DNS on the rootless CNI network | the plugin `dnsname` (CNI) / `aardvark-dns` (netavark); `podman.sh` installs it with apt only on a runner (`GITHUB_ACTIONS=true`), else fails with a hint |
| D8 `run` (and `TestRunDev`) got no connection | the default listen/broker host is the bridge gateway `10.88.0.1`, not a host address under rootless networking | `--listen`/`--broker-host` = host address (`ip -4 route get`), `OEC_LIVE_RUN_LISTEN` in `TestRunDev`; `liveArch` reads `{{.Host.Arch}}` from `podman info` (Docker: `{{.Architecture}}`) – test code only |
| rootless overlay `exec …: Invalid argument` | nested in Docker Desktop only | `vfs` in `linux-images.sh`; a runner needs it not |

Not checked: Podman 5 (pasta networking), `podman-compose` (1.x has no `--wait`). Documented in `oec/dev/README.md` "Platforms and Podman (C-107)", `oec/conformance/README.md` (Podman run example), the Community pages.

### 5. Found and fixed

1. `getting-started.sh` waited for the registry to appear in its own asset list – the registry lists the other participants, not itself (`c4d0939`; the script was wrong).
2. A stale volume of an own manual Podman stack made the registry see a DataSetWriterId conflict – own leftover, removed; no code change.
3. The confirmation run of `linux-images.sh` with Podman failed in `podman: getting-started`: `go run ./pki` refused the `oec/dev/generated` left by the Docker run before (`pki: generated exists`). The same order runs on the runner. `getting-started.sh` now reuses `generated/` as `live.sh` does (test first in `TestImages`, `1b0736c`).
4. The second confirmation run (`1b0736c`, Docker part) failed in the story step: the stack came up in 0 s, the config service had discovered the Config of the weather service but not yet its SubscriptionList and answered the `Set` with 409 "not writable" (SF-107) – correct; the script now polls until the Config is listed `writable` and the application `online` (test first in `TestImages`, `358869a`).

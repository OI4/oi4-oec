# C-096 – P4b: ESP-IDF port, example firmware, D7 in Espressif QEMU

- Date: 2026-11-12
- Phase: P4b – Micro SDK (D9), increment 5 of 6 (ADR-0030 §10)
- PO input: none new (C-091 addendum 1: P4b in one session; ask only when something really does not work, is unclear or needs a guideline change).
- Baseline: guideline `52d8470` (unchanged since C-078), SF-001 … 117 resolved, next SF-118.

## Goal

The reference port of the micro SDK on ESP-IDF (ADR-0024): a PAL on esp-mqtt, esp-tls/mbedTLS and NVS, an example firmware for `esp32` and `esp32s3`, the firmware judged by D7 in the Espressif QEMU (opt-in, ADR-0030 §8), and the RAM/flash footprint on the ESP32.

## What was done

1. **Toolchain (opt-in, outside the workspace):** ESP-IDF **v6.1** in `~/esp/esp-idf-v6.1` (tools in `~/.espressif`), Espressif QEMU `esp_develop_9.2.2_20260417` (`idf_tools.py install qemu-xtensa`). IDF 6.1 ships mbedTLS 4.1.0 (TLS 1.2 and 1.3 only; IP SANs are checked). esp-mqtt comes from the ESP Component Registry (`espressif/mqtt` 1.1.0, Apache-2.0; ADR-0024).
2. **Component** `oec/sdk/micro/port/esp-idf/oecm/` (ESP-IDF names a component after its directory, so not `port/esp-idf/` itself): `CMakeLists.txt` (the core sources of `src/` + `oecm_esp.c`, `REQUIRES mqtt`), `idf_component.yml` (`idf >=6.0`, `espressif/mqtt ^1.1.0`), `include/oecm_esp.h` (71 lines), `oecm_esp.c` (322 lines). The PAL:
   - `oecm_esp_init(cfg, &port, &pal)`: `uri` (`mqtts://` only), `ca_pem` (required), user/password or client certificate/key, NVS namespace (default `oecm`), `rx_size` (default 8192); allocates the receive buffer and a ring buffer once.
   - `mqtt_connect`: the client is created once; before every connect the new Will is set with `esp_mqtt_set_config` (REQ-LIFE-008/016) and the client is reconnected (`esp_mqtt_client_reconnect`, or `esp_mqtt_client_start` after a stop); `disable_auto_reconnect`, the core's backoff decides. `mqtt_disconnect`: `esp_mqtt_client_stop` (DISCONNECT, no Will).
   - Events: the esp-mqtt handler only queues (it can run inside `esp_mqtt_client_publish` on the application task); items carry a connection generation, so events of an earlier attempt are dropped; fragmented DATA events are reassembled up to `rx_size` (larger messages are dropped with a warning). `oecm_esp_dispatch(port, dev, wait_ms)` hands them to `oecm_on_connected`/`oecm_on_disconnected`/`oecm_on_message` on the application task – the core stays single-threaded.
   - `unix_time_ms` (`gettimeofday`), `monotonic_ms` (`esp_timer_get_time`), `persist_load`/`persist_save` as NVS blobs (`len` 0 erases; without NVS the persistence stays NULL, so Level 3 is refused by `oecm_init`).
3. **Shared sensor:** the simulated temperature sensor moved with `git mv` from `host/cmd/oecm-host/demo.c` to `examples/sensor/oecm_sensor.c` (+ `oecm_sensor.h`; `oecm_sensor_setup`, `oecm_sensor_interval_s`, `oecm_sensor_tick`), the Config label "Host sensor" became "Temperature sensor"; the host runner includes it through `sensor.c` (cgo). Host runner and firmware run the same device code.
4. **Example firmware** `examples/esp-idf/` (ESP-IDF project `oecm_example`, `PROJECT_VER` 0.1.0, `MINIMAL_BUILD`):
   - `main/main.c` (306 lines): reads the provisioning (partition `oecprov`, namespace `oec`: `uri`, `ca`, `user`/`password` or `cert`/`key`, `serial`, `level`, `max_packet`, `ntp`, `wifi_ssid`/`wifi_pass`), brings up Wi-Fi (station) or OpenCores Ethernet (QEMU), sets the clock by SNTP or the console, waits for a plausible time (≥ 2023), builds the MAM (Manufacturer OI4, Model "OEC Micro ESP32"/"… ESP32-S3", ProductCode `OECM-ESP32`/`OECM-ESP32S3`, SerialNumber from the provisioning or the base MAC, HardwareRevision from the chip info, SoftwareRevision from the app description, DeviceClass "Sensor"), runs the sensor at Level 1 … 3 (Kconfig default 3) and loops `oecm_esp_dispatch` (≤ 200 ms) + `oecm_poll` + the sensor tick; every 60 s it logs the free heap and the unused stack. The serial console takes `stop` (Close, DISCONNECT, `oecm: stopped (ok)`) and `time <unix ms>`.
   - `partitions.csv` (`nvs` 0x9000/24 KB, `phy_init`, `oecprov` 0x10000/24 KB, `factory` 0x20000/1.9 MB), `sdkconfig.defaults` (4 MB flash, main task stack 8192, `-Os`, MQTT 3.1.1 over TLS only, mbedTLS, **no certificate bundle**), `sdkconfig.qemu` (OpenCores Ethernet, 10 RX DMA buffers), `main/Kconfig.projbuild`, `dependencies.lock` (committed; target `esp32`).
   - `build.sh [esp32|esp32s3|qemu]` (opt-in): builds into `oec/sdk/micro/target/esp-idf/<variant>/`, prints `idf.py size` and the component sizes. `.gitignore`: `managed_components/`, `sdkconfig`, `sdkconfig.old`, `build/` of the example.
5. **QEMU runner** `host/cmd/oecm-qemu` (Go, standard library only; 4 files, 685 lines with the tests): reads the container storage below `OEC_ROOT` like `oecm-host` (hostname → SerialNumber, `broker.json`, CA, credentials or client certificate); a loopback broker address becomes 10.0.2.2 (the host in the QEMU user network); creates `flash.bin` once (`esptool merge-bin` of the build, 4 MB) and seeds the `nvs` partition with the state files `oecm.refdes`/`oecm.wid` (the D7 Level 3 seeding of C-095); rewrites `oecprov` on every start (`esp_idf_nvs_partition_gen`); starts `qemu-system-xtensa -machine esp32 -nic user,model=open_eth -serial stdio`, answers "waiting for the time" with `time <ms>`, turns SIGTERM/SIGINT into `stop` (10 s, then kill). Flags `-build`, `-qemu`, `-python`, `-level`, `-state`, `-host-addr` (env `OECM_QEMU_BUILD`, `OECM_QEMU`, `OECM_QEMU_PYTHON`).
6. **D7 harness:** the pinned passes moved from `cmd/oecm-host/main_test.go` to `internal/d7run/pins.go` (`Level1Pass`, `Level2Pass`, `Level3Pass`, `RefdesSeed`) and are shared by both runners; `d7run.D7` gained `ProxyNames` (`--proxy-name`, the IP SAN 10.0.2.2 of D7's proxy certificate), `Timeout` (default 3 s) and `RestartWait` (default 15 s); package doc updated.
7. **Tests:** `cmd/oecm-qemu/main_test.go`: `TestProvisioning` and `TestPartitions` (unit, in the gate); `TestQEMUD7Level1/2/3` (opt-in: skipped without `OECM_QEMU_BUILD` and `OECM_QEMU`, also with `OECM_REQUIRE=1`; QEMU never runs in the gate, ADR-0030 §8).
8. README (component, provisioning, console, QEMU runner, footprint), ADR-0030 amendment C-096, `check.sh` header comment.

## Results

Builds (ESP-IDF v6.1, all three variants without a compiler warning):

| | `esp32` | `esp32s3` | `qemu` (`esp32`) |
|---|---|---|---|
| app image | 883 960 B | 878 842 B | 535 856 B |
| flash code / data | 652 868 / 128 984 B | 649 220 / 132 152 B | 372 004 / 107 136 B |
| IRAM / DRAM (static) | 84 431 / 49 877 B | 16 384 IRAM + 110 730 DIRAM | 45 563 / 29 377 B |
| `liboecm.a` (core + PAL; flash only) | 33 584 B | 33 676 B | 33 026 B |
| esp-mqtt | 11 190 B | 11 755 B | 10 752 B |
| mbedTLS | 24 276 B | 24 249 B | 24 308 B |

The core + PAL use about 33.6 KB of flash and no static RAM; the firmware's static buffers (device 1 KB, transmit 8 KB, ReferenceDesignation 2 KB) are in its `.bss`; the PAL allocates 8 KB receive buffer and about 16 KB ring buffer at init. Wi-Fi accounts for most of the difference to the `qemu` variant.

D7 against the firmware in the Espressif QEMU on the Rust SDK test broker (`go test -run TestQEMUD7 ./cmd/oecm-qemu`, opt-in, final run after the rebuild; reports in `/tmp`, not committed):

| Run | Result | Duration |
|---|---|---|
| D7 `test --level 1` | **21 pass, 5 warn, 29 skip, 0 fail** – the host pins exactly | 245 s (the restart hook reboots QEMU) |
| D7 `test --level 2` | **38 pass, 3 warn, 14 skip, 0 fail** | 95 s |
| D7 `test --level 3` (stored ReferenceDesignation) | **50 pass, 0 warn, 5 skip, 0 fail** | 70 s |

The firmware passes the same D7 tests as the core in the host runner: the connection tests T7-CON-01 … 04 (TLS handshake, CONNECT with Will, through D7's proxy with the IP SAN 10.0.2.2), the lifecycle tests with a real reboot of the device (T7-LIFE-04, T7-SET-10: the ReferenceDesignation in NVS survives the restart) and all request tests.

Opt-in run against the dev broker `oec/dev` (Mosquitto 2.1.2, TLS, password file, ACL): `go run ./pki -force -san 10.0.2.2` (the broker certificate needs the address the device uses), broker only; the QEMU device at Level 3 with the storage `generated/roots/oec-dev-app` (`oi4.org/OEC,20Micro,20ESP32/OECM-ESP32/oec-dev-app`):

- D7 `oec-check test --level 3` with the probe user `oec-probe`: **38 pass, 0 fail, 17 skip** (exit 4, inconclusive without `--allow-skip`): the skips need the proxy, the restart hook or a peer (T7-CON-*, T7-LIFE-*, T7-ADR-01, T7-SET-10), the connect before the run (T7-MON-03) or have nothing to observe. A first attempt with the unprivileged certificate client `oec-dev-cert` had 12 fails for every `Set`/`Del`/`Call`: the dev ACL drops these requests from every user except `oec-probe` (C-071) – a test setup error, not a defect.
- D7 `monitor` (25 s) during the SIGTERM of the runner: the Close of the device was seen (1 message, 0 invalid); the device printed `oecm: stopped (ok)`.

Device observations (QEMU): IP after about 3.5 s, connected about 2 s later (TLS handshake in emulation); free heap at least 167 KB at Level 3 (lowest during the dev run; 173 … 176 KB in the D7 runs); the 8 KB main task used at most 2.4 KB of stack (lowest unused 5 828 B). Harmless log lines: the OpenCores MAC has no multicast filter (`eth_set_mac_filter`); "RX frame dropped" went from many to at most 3 per run after `CONFIG_ETH_OPENETH_DMA_RX_BUFFER_NUM=10` (the default 4 buffers overflowed under D7's bursts; TCP retransmits, no test was affected); the TLS errors `-0x2700`/`-0x6E80` are the device rejecting D7's deliberately invalid broker certificates (T7-CON-*).

Defects found during the cycle: none in the core, D7 or the SDKs. Port pitfalls handled in the design (found while writing the PAL against the esp-mqtt sources): the esp-mqtt event handler can run inside `esp_mqtt_client_publish` on the application task (calling the core from it would re-enter the core – so it only queues); `esp_mqtt_client_reconnect` only works in the reconnect wait state (fallback stop + start); a failed connect reports DISCONNECTED (the generation tag drops it after a newer attempt).

## Agent decisions (G-3.4 b)

- **A-467 Component path:** `oec/sdk/micro/port/esp-idf/oecm/` (ESP-IDF derives the component name from the directory; ADR-0030 §1 amended); `examples/esp-idf/main/idf_component.yml` refers to it by path; esp-mqtt `^1.1.0` from the Component Registry, `dependencies.lock` committed.
- **A-468 PAL design:** events through a FreeRTOS ring buffer with a connection generation to the application task (`oecm_esp_dispatch`), no auto-reconnect, the Will per connect via `esp_mqtt_set_config`, fragment reassembly up to `rx_size` (default 8192), `persist_*` as NVS blobs in the namespace `oecm`; buffers are allocated once at init (the core itself stays heap-free).
- **A-469 Provisioning partition:** the example firmware compiles nothing of a site in; it reads broker, CA, credentials or client certificate, SerialNumber, level, MaxPacketSize, SNTP server and Wi-Fi from the NVS partition `oecprov` (namespace `oec`), written with the IDF NVS generator and flashed separately (README). Without `max_packet` the core assumes 262144 (`oecm_config.max_packet_size` 0).
- **A-470 Serial console:** `stop` (graceful stop with Close) and `time <unix ms>` (clock without SNTP: QEMU runs and boards without internet); the console can be disabled in Kconfig.
- **A-471 Shared sensor:** `examples/sensor/` is the device code of the host runner and the firmware (moved with history); the Config label is "Temperature sensor".
- **A-472 QEMU runner:** `host/cmd/oecm-qemu` takes the same container storage as `oecm-host` and maps it to the provisioning; loopback → 10.0.2.2; the flash image is kept in the state directory, NVS seeded from the state files on creation; clock and stop over the console.
- **A-473 Shared D7 pins and options:** the pins live in `internal/d7run/pins.go`; `D7.ProxyNames`, `D7.Timeout` (QEMU 5 s) and `D7.RestartWait` (QEMU 1 min) are additive (defaults unchanged for the host runner).
- **A-474 QEMU stays opt-in:** `TestQEMUD7Level1/2/3` need `OECM_QEMU_BUILD` and `OECM_QEMU` (and ESP-IDF's Python for the image tools); without them they skip even under `OECM_REQUIRE=1`. Only the unit tests of the runner run in the gate (ADR-0030 §8).
- **A-475 QEMU network buffers:** `sdkconfig.qemu` sets 10 RX DMA buffers of the OpenCores MAC (QEMU variant only).
- **A-476 TLS settings:** TLS via esp-tls/mbedTLS 4.1 (TLS 1.2/1.3), the broker CA from the provisioning only, no certificate bundle (ADR-0024: the dev CA is private), MQTT 3.1.1 only, no WebSocket transport, `-Os`.
- **A-477 Footprint:** core + PAL 33.6 KB flash and no static RAM on the ESP32; app images 884 KB (`esp32`), 879 KB (`esp32s3`), 536 KB (`qemu`); free heap ≥ 167 KB, main stack ≤ 2.4 KB (table above, README).
- **A-478 Dev broker run:** against `oec/dev` the D7 `test` must use the probe user (ACL, C-071), and the PKI needs `-san 10.0.2.2` for a QEMU device (`oec/dev/README.md` already documents `-san`); this run stays a manual opt-in step in the log (no automation: the D7 run on the test broker covers the same tests and more).

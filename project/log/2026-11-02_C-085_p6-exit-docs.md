### 5. Defect 2 – the answer to a `Set` replaced the on-change publication (A-378, test first)

Analysis: the Rust core treated the answer as the publication – `apply_set_config` cleared the pending flag of the Config, `apply_set_data` marked the DataSet as answered, and a changed ReferenceDesignation was never published unsolicited although its entry has Mode `ON_REQUEST_SOURCE_10`. The reviewed notes of REQ-RES-DATA-012 and REQ-RES-CONFIG-022 say that the publications configured in the PublicationList follow on their own (REQ-MQTT-019); D7 (A-220) and ADR-0026 §15.3 ("after every effective change") agree. So this is an SDK defect, not a gap in the guideline: **no SF**.

The C ABI and the Go SDK are bindings over this core, so one fix covers all three demos.

- Tests first (each failed before the fix): `oec-core/tests/provider_config.rs` `the_application_decides` (after an accepted changing `Set` the next poll gives one `Pub/Config` without `ReplyTo` with the new value; an unchanged `Set` gives none), `provider_write.rs` `set_data_completion_answers_as_decided` (`Pub/Data` without `ReplyTo`, payload `{"T":1.5,"N":"7"}`; the same values again give none), `provider_refdes.rs` `the_application_decides` (one unsolicited `Pub/ReferenceDesignation`; an identical `Set` none); `oec/tests/runtime.rs` `config_is_got_set_and_persisted` expects the on-change publication (interval "20" after the first `Set`, "30" after `decided_sets`).
- Fix in `oec-core`: `provider/config.rs` (`pending |= changed`), `provider/write.rs` (no `answered()`; `Set::answered` removed from `sets.rs`), `provider/refdes.rs` (a changing `Set` queues its source, new `refdes_changes` publishes it without `ReplyTo`), `provider.rs` (`refdes_pending`; `changes()` calls `refdes_changes` after `config_changes`). Doc comments in `oec` (`config.rs`, `data.rs`, `asset.rs`) and the `Set` pipeline of `oec/sdk/rust/README.md` say that the publication follows.
- No API or ABI change (ABI version 1), no new dependency. Recorded in ADR-0026 amendment C-085 (§21).

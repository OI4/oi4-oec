## Work

### MQTT client for D2 – `rumqttc` is out

Sources: crates.io API, GitHub, RustSec advisory DB, 2026-10-26. ADR-0011 and the research notes assumed `rumqttc` as the natural MQTT client. The check showed it is effectively unmaintained:
- Last release 0.25.1 (2025-11).
- It pins `rustls-webpki ^0.102.8`, which has 5 open RustSec advisories (RUSTSEC-2026-0049, -0098, -0099, -0104, -0382). They are fixed only in 0.103.x.
- It also pins the unmaintained `rustls-pemfile` (RUSTSEC-2025-0134).
- The bump PRs #1072/#1073 were closed without merge; issues #1046/#1067 are open.
- In #1029 the maintainer said the project is deprioritized.
- A custom TLS stream cannot be injected: pre-setting `EventLoop.network` skips CONNECT.

Alternatives checked:
- **`rumqttc-v4-next` 0.34.0:** an active fork with current webpki, but one maintainer.
- **`paho-mqtt`:** Eclipse, a C library with OpenSSL; EPL-2.0/EDL-1.0; harder cross and Windows builds.
- **`ntex-mqtt`:** its own runtime; MSRV 1.97.
- **`mqtt-protocol-core`:** one maintainer, low adoption.

The OEC subset of MQTT 3.1.1 is small and frozen:
- QoS 0/1, no retain, clean session;
- a Will per connect, keep alive 60 s;
- REQ-MQTT-001/014/015/017/018, REQ-LIFE-016.

The agent therefore recommends an own sans-IO codec and session in `oec-core`. This fits the S4 layering (ADR-0011: sans-IO core). It is recorded as Q-026: (a) own codec, recommended; (b) `rumqttc-v4-next`; (c) `paho-mqtt`. The PO was asked live and was not available, so it stays an open question.

### ADR-0023 – D2 dependencies (proposed)

- **Runtime:** tokio (`current_thread` for `run()`).
- **MQTT:** own codec (Q-026 a).
- **TLS:**
  - rustls 0.23 + tokio-rustls, TLS 1.2/1.3 only (REQ-MQTT-005);
  - provider aws-lc-rs, with feature `crypto-ring`;
  - trust only from the bus storage; no `webpki-roots`, no `rustls-pemfile`.
- **JSON:** serde/serde_json.
- **Schema validation:** jsonschema `=0.60.1` behind `strict-validation`, raised together with `rust-check`.
- **Small crates:** thiserror, `log` (+ optional `tracing`), `time`, uuid.
- **Tooling:**
  - cbindgen as a CLI, with the header committed and diffed;
  - cargo-deny from P4 (license allowlist without EPL/MPL/GPL in linked code);
  - MSRV 1.89, edition 2024;
  - cargo-zigbuild as the cross-build candidate.
- Each choice comes with its rejected alternatives.

### ADR-0024 – D9 libraries (proposed)

Facts checked on 2026-10-26:
- **ESP-IDF:** v6.1 is current. Since IDF 6, `mqtt` and `json` (cJSON) are managed components, not part of IDF.
- **esp-mqtt** v1.1.0 (Apache-2.0): a Will per connect works with `disable_auto_reconnect`, then `esp_mqtt_set_config` (which copies the new Will), then `esp_mqtt_client_reconnect` in state `WAIT_RECONNECT`. Read in `mqtt_client.c`; to be verified on hardware in P4b.
- **Arduino-ESP32** (3.3.12, 4.0.0-RC1): third-party libraries use esp-mqtt from the core, so the Arduino port reuses the ESP-IDF PAL. Fallback: `arduino-mqtt` (MIT; `setWill` before each `connect`; TLS via `NetworkClientSecure`).
- **Not chosen:**
  - `PubSubClient` (no release since 2020, QoS 0 publish only);
  - `ArduinoMqttClient` (LGPL-2.1).
- **jsmn:** last commit 2021, abandoned under G-4.4.
- **cJSON:** heap; no longer bundled with IDF 6.

Decision:
- own JSON encoder plus an own bounded pull reader (no heap; fuzzed on the host);
- Unity (v2.7) with CMake/CTest, plus the ESP-IDF test app;
- ASan/UBSan and libFuzzer on the host;
- SNTP, NVS/Preferences;
- M5Unified only in the demo.

The JSON reader choice is Q-027: (a) own reader, recommended; (b) cJSON with a static arena.

# C-094 – P4b: micro core Level 2, D7 Level 2 in the gate, fuzzing

- Date: 2026-11-10
- Phase: P4b – Micro SDK (D9), increment 3 of 6 (ADR-0030 §10)
- PO input: none new (C-091 addendum 1: P4b in one session; ask only when something really does not work, is unclear or needs a guideline change).
- Baseline: guideline `52d8470` (unchanged since C-078), SF-001 … 117 resolved, next SF-118.

## Goal

Messaging Level 2 in the C17 core: a bounded JSON pull reader and topic parser, `Get`/`Set` with Status events, Data and Config definitions, own number formatting. The core is judged by D7 `oec-check test --level 2` in the gate, with libFuzzer targets for the parsers.

## What was done

1. **Core, new sources** (`oec/sdk/micro/src/`, C17, no heap, no stdio, the symbol allowlist of ADR-0030 §2 unchanged):
   - `oecm_num.c`: decimal output of integers and of `double` with a fixed number of decimals (no `printf`, no float formatting from the C library), the JSON number grammar, `parse_f64`, RFC 3339 time, SHA-1 and UUIDv5 (DataSetClassId);
   - `oecm_json.c`: a bounded JSON pull reader (no tree, no recursion, nesting depth at most `OECM_JSON_DEPTH` 16; spans into the received payload; UTF-8, escapes and surrogate pairs checked, duplicate keys found);
   - `oecm_topic.c`: the topic parser (`Oi4v2/<ServiceType>/<AppId>/<Method>/<Resource>[/<Source>[/<Filter>]]`, AppId and Source as base64url of the Identification Link);
   - `oecm_res.c`: the encoders of Profile, Data, Metadata, Config (sensitive values masked, REQ-RES-CONFIG-024), PublicationList, SubscriptionList and the Status event; answers with pagination (REQ-PAG-002 … 008: a single message when it fits the transmit buffer and `MaxPacketSize`, else pages of the largest count that fits; `PerPage`/`Page` of a PaginationRequest); the Level 2 checks of `oecm_init`; the subscriptions and publications after a connect;
   - `oecm_req.c`: the request handling – `Get` of MAM, Health, Profile, Data, Metadata, Config, PublicationList and SubscriptionList; `Set` of Data, Config, PublicationList and SubscriptionList, `Del` of SubscriptionList; every `Set`/`Del` answered with a Status event (`Pub/Event/<AppId>/Status/<Good|Bad>`, REQ-RES-EVENT-005, REQ-CMP-043) with the decision of the Rust provider (`oec-core` `provider.rs`, `provider/write.rs`, `config.rs`, `sublist.rs`).
2. **API** (`include/oecm.h`, additive): `oecm_field`, `oecm_data`, `oecm_cfg_object`/`group`/`context` and the Level 2 members of `oecm_config` (`data`, `config`, `on_config`, `on_data`, `app_ctx`), `oecm_data_changed`. Values live in the application; the core reads them when it publishes and writes them only on an accepted `Set`. `OECM_DATA_MAX` 8, `OECM_FIELDS_MAX` 16, `OECM_CONFIG_MAX` 4.
3. **Unit tests** (Unity, ASan + UBSan): `test_num` 7, `test_topic` 3, `test_reader` 6 (new), `test_level2` 26 (new: connect order, every `Get`, pagination, `Set Data`/`Config` valid and invalid with the Status codes, reserved config names, `Set PublicationList` and `Set`/`Del SubscriptionList`, Locale/Query helper DSMs, malformed requests), `test_device` 18 (Level 3 → `OECM_E_LEVEL`, Level 1 with definitions → `OECM_E_LEVEL`). All 72 Unity tests pass.
4. **Payload check:** `tests/emit.c` adds a Level 2 lifecycle with 8 `Get` requests, a valid and an invalid `Set Config` and a `Set Data`; D7 `oec-check validate`: **36 messages, 0 invalid**.
5. **Host runner:** `cmd/oecm-host/demo.c`, a simulated temperature sensor (Data `Temperature`: Value, Setpoint, Label; Config context `Sensor`, group `General`: Interval 1 … 3600 s, Label), `-level 2` in `main.go` (transmit buffer 8192 octets, the demo value changes every Interval); `d7run` passes extra runner arguments (`Args`).
6. **D7 Level 2 in the gate:** `TestD7Level2` with **38 pinned passes**; `TestD7Level1` stays (21 passes).
7. **Fuzzing** (`fuzz/`, ADR-0030 §6): targets `fuzz_json` (the reader over a whole document), `fuzz_topic` (the parser), `fuzz_message` (topic suffix + payload into a connected Level 2 device with 2 Data and 5 Config objects; traps when a publication is not below `Oi4v2/` or its payload is not valid JSON); `replay.c` replays a corpus without libFuzzer; seed corpora (7 JSON, 7 topics, 14 messages); ctest `fuzz_json`, `fuzz_topic`, `fuzz_message` replay them under ASan/UBSan (gate); `fuzz/run.sh [SECONDS] [TARGET…]` fuzzes with libFuzzer (opt-in) and replays the grown corpus under ASan/UBSan.
8. `oec/sdk/micro/check.sh` header (D7 Level 1 and 2, fuzz replay, Level 2 emitter), README, ADR-0022 and ADR-0030 amendments C-094.

Two gate-side observations:

- **T7-MON-05 after sleep:** one micro check failed T7-MON-05 with a 9 min 45 s gap in a 130 s run – the Mac slept although `caffeinate -i` ran (idle sleep only). The rerun with `caffeinate -dims` passed. Not a defect.
- **ASan of Homebrew LLVM 21 hangs on macOS 27:** a libFuzzer binary with `-fsanitize=fuzzer,address` hangs at start-up before any output, also for an empty target; `fuzzer,undefined` works. `fuzz/run.sh` therefore fuzzes with UBSan on macOS and replays the grown corpus under ASan + UBSan built by the system compiler (A-454).

## Agent decisions (G-3.4 b)

- **A-446 Level 2 scope:** `Get` of MAM, Health, Profile, Data, Metadata, Config, PublicationList, SubscriptionList; `Set` of Data, Config, PublicationList, SubscriptionList; `Del` of SubscriptionList; Status events. PublicationList and SubscriptionList moved from C-095 into C-094: a Level 2 device lists its publications and its subscriptions (the `Set` topics) and D7 `--level 2` requests them. `Get`/`Set`/`Del ReferenceDesignation`, `NewDataSetWriterId`, persistence: C-095.
- **A-447 Definitions instead of callbacks with status** (ADR-0022 §9 amended): the application describes Data fields and Config objects statically with pointers to its own variables; the core validates a `Set` completely (types, Validation Length/Min/Max/Values, writability) and writes the values only if the whole `Set` is valid, then calls `on_config`/`on_data`. The sketched `oecm_add_data`/`oecm_on_set` returning a status code are dropped: the decision is the same as in the Rust provider and needs no status logic in the application.
- **A-448 DataSetWriterIds** (ADR-0030 §9 refined): MAM 10, Health 11, Profile 12, PublicationList 13, Status events 14 (Good), 15 (Uncertain), 16 (Bad), SubscriptionList 17, then the Config contexts and the Data DataSets from 18 in definition order (Metadata shares the id of its Data). Inbound ids 1 … 9 are the helper DataSets (REQ-MSG-019): the PaginationRequest (1) is used, Locale (3) and Query (9) are accepted and ignored (all texts are en-US); a `Set`/`Del` needs exactly one DataSetMessage besides the helpers, else `BadInvalidArgument`. Answers carry the Pagination DataSetMessage with id 2.
- **A-449 Decision order** where the Rust provider's order depends on its data structures: the first violation is reported in document order of the request (Rust: key order of its maps); the MessageId pattern is checked on the raw token; duplicate keys are checked all and the last one applies; a value larger than its buffer → `BadOutOfRange`; a TopicPath that does not fit the transmit buffer → `BadInvalidArgument`; every list entry is `NONE_0` configurable, so any change of a PublicationList entry → `BadNotWritable`; the Validation `Pattern` of a Config object is not supported (no regex engine on the device; the definition type has no Pattern member).
- **A-450 Own number formatting:** `double` values are written with the field's `decimals` (0 … 9) by integer arithmetic; beyond 15 … 17 significant digits the last digit may differ from a correctly rounded result (documented in the header). Inbound numbers are checked against the JSON number grammar and converted by the core.
- **A-451 Subscriptions before the Birth:** after CONNACK the device subscribes to its request topics first, then publishes Birth and Health, as the Rust SDK does; a request right after the Birth is not lost.
- **A-452 No Syslog:** the device publishes no Syslog events, so it has no log levels to configure (REQ-TOP-027, SHOULD, MG 7.7 best practice; T7-SET-12 skipped). A device that logs over the bus can be added later without an API break.
- **A-453 Init checks:** Level 1 with Data or Config definitions → `OECM_E_LEVEL`; Level 3 → `OECM_E_LEVEL` until C-095; ConfigName `Name`/`Description`, GroupName `Context` and names not matching `[A-Za-z_][A-Za-z0-9_-]*` → `OECM_E_ARG` (as Rust `check_definition`).
- **A-454 Fuzzing:** three targets in `fuzz/`, seed corpora replayed in the gate (ctest, ASan + UBSan), `fuzz/run.sh` opt-in. Homebrew LLVM 21's ASan runtime hangs on macOS 27, so on macOS the libFuzzer run uses UBSan only and ASan comes from the replay of the grown corpus (`OECM_FUZZ_SAN` overrides; Linux uses `fuzzer,address,undefined`). The grown corpora stay in `target/fuzz` and are not committed.
- **A-455 Both D7 runs in the gate** (revises A-445): Level 1 (no definitions, 21 passes) and Level 2 (the demo sensor, 38 passes) are different code paths of the core, so both stay; step 9 now takes about 4 min.
- **A-456 Sizes:** `OECM_DEVICE_SIZE` stays 1024 (Level 2 uses 568 octets on a 64-bit host); `OECM_TX_MIN` stays 2048 (Level 1 bound); a Level 2 device needs a larger transmit buffer for its Config and Metadata answers (the host demo uses 8192). `oecm_init` encodes the Birth with the longest MessageId; larger answers are paginated (REQ-PAG-005) and a page that does not fit even with one item is not sent (`OECM_E_NOSPACE` internally).
- **A-457 macOS fortify flag:** the plain core build for the symbol check uses `-U_FORTIFY_SOURCE -D_FORTIFY_SOURCE=0` so the checked `memset` of the macOS headers is not lowered to `bzero` (not on the allowlist).
